## 1. Общая архитектура

Один долгоживущий процесс `python3 -m bot` (новый пакет `bot/` рядом с
`pipeline/`; существующий код не правим до сверки):

- **aiogram 3.x** Dispatcher, long polling — единственный консьюмер
  `getUpdates` (решение D15).
- Внутри процесса — **asyncio-планировщик** слотов отправки и catch-up
  (решение D13).
- Сбор источников выполняется в момент отправки сводки (слот или команда) —
  один код-путь (решение D14).
- Конфигурация и данные — SQLite, новый файл `bot.db`, WAL (решение D12).
- launchd только держит процесс живым (KeepAlive); догоняющая логика —
  по `last_sent_at`, а не по календарю launchd.

```
Telegram ──long polling──> aiogram Dispatcher
                              │
              handlers/ (FSM: онбординг, меню, CRUD, settings, /digest)
                              │
                              v
                           db.py ──── bot.db (users, sources, items, digests)
                              │
scheduler.py ── слот / catch-up / FSM-timeout sweeper
                              │
                              v
            digest.py: collectors/* → items дельты → llm.py (GLM | mock)
                              │
                              v
            tgsend.py (экранирование, split ≤4000, chat actions) → Telegram
```

### 1.1 Модули и зоны ответственности

| Модуль | Зона ответственности |

### 1.2 Схема БД (`bot.db`, SQLite, WAL)

```sql
CREATE TABLE users (
  chat_id      INTEGER PRIMARY KEY,          -- Telegram chat id
  tz_offset_min INTEGER NOT NULL DEFAULT 180,-- МСК (решение D18)
  send_times   TEXT NOT NULL DEFAULT '["09:00"]', -- JSON-массив "HH:MM", 1..2 слота (P0)
  last_sent_at TEXT,                         -- ISO8601 UTC; NULL = сводок ещё не было
  created_at   TEXT NOT NULL,
  onboarded_at TEXT
);

CREATE TABLE sources (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id    INTEGER NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  kind       TEXT NOT NULL CHECK (kind IN ('rss','html','tgweb','reddit','twitter')),
  url        TEXT NOT NULL,   -- канонический адрес: feed URL / страница / имя канала / имя сабреддита / имя аккаунта
  title      TEXT NOT NULL,
  topics     TEXT NOT NULL DEFAULT '[]',     -- JSON-массив тегов
  origin     TEXT NOT NULL DEFAULT 'survey' CHECK (origin IN ('survey','manual')),
  enabled    INTEGER NOT NULL DEFAULT 1,
  status     TEXT NOT NULL DEFAULT 'ok' CHECK (status IN ('ok','degraded','error')),
  status_msg TEXT,
  added_at   TEXT NOT NULL,
  UNIQUE (chat_id, kind, url)
);
CREATE INDEX idx_sources_chat ON sources (chat_id, enabled);

CREATE TABLE items (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  source_id    INTEGER NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
  url          TEXT NOT NULL,
  title        TEXT NOT NULL,
  published_at TEXT NOT NULL,   -- ISO8601; fallback = fetched_at
  fetched_at   TEXT NOT NULL,
  url_hash     TEXT NOT NULL,   -- sha256(url + '|' + title), решение D19
  UNIQUE (source_id, url_hash)
);
CREATE INDEX idx_items_published ON items (published_at);

CREATE TABLE digests (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id      INTEGER NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  period_from  TEXT NOT NULL,
  period_to    TEXT NOT NULL,
  item_count   INTEGER NOT NULL,
  message_text TEXT NOT NULL,
  created_at   TEXT NOT NULL
);
CREATE INDEX idx_digests_chat ON digests (chat_id, created_at);
```

Связи: `users 1—N sources 1—N items`; `users 1—N digests`.

Ключевые решения по данным:

- Дедуп — `UNIQUE(source_id, url_hash)` (D19); повторный сбор —
  `INSERT OR IGNORE` (NFR-03).
- Окно дельты — по `items.published_at` (при отсутствии даты у источника —
  `fetched_at`).
- Плановая отправка фиксируется транзакционно: запись в `digests` +
  обновление `users.last_sent_at` одной транзакцией — это защита от дублей
  при catch-up.
- `news.db` не открывается ботом на запись (NFR-07); опциональный импорт
  истории — offline-скрипт `scripts/import_news_db.py` (ATTACH read-only +
  `INSERT ... ON CONFLICT DO NOTHING`), по умолчанию не запускается.

### 1.3 FSM диалога

Хранилище состояний P0 — MemoryStorage aiogram (перезапуск бота = сброс
диалогов; настройки живут в БД, потерь нет). Точка отсчёта таймаута —
timestamp последнего апдата пользователя с активным состоянием; sweeper
в `scheduler.py` проверяет раз в ~60 с; порог 10 минут (D17).

**Онбординг (и повторный опрос):**

| Состояние | Что происходит | Переходы |
|---|---|---|
| `ObTopics` | Мультивыбор тем inline-кнопками; «Далее» | → `ObSources` |
| `ObSources` | Подборка каталога по темам, все предвыбраны; можно исключить; «Далее» | → `ObFreq` |
| `ObFreq` | 1 раз в день / 2 раза в день | → `ObTime` |
| `ObTime` | Пресеты (09:00, 21:00…) + ввод `HH:MM` текстом | → `ObConfirm` |
| `ObConfirm` | Резюме; «Сохранить» / «Пройти заново» | Сохранить → нет состояния, главное меню |

Повторный опрос: предварительное состояние `RsMode` («Заменить» / «Добавить поверх»)
→ далее те же `Ob*`; финализация зависит от режима (D22, FR-03):

- Режим A: `DELETE FROM sources WHERE chat_id=? AND origin='survey'` →
  вставка нового набора.
- Режим B: `INSERT OR IGNORE`-объединение по `UNIQUE(chat_id, kind, url)`.

**Мастер добавления источника:**

| Состояние | Что происходит | Переходы |
|---|---|---|
| `AsKind` | Тип: RSS / сайт / TG-канал / subreddit / X-аккаунт | → `AsUrl` |
| `AsUrl` | Ввод адреса текстом; валидация под тип; невалидно → сообщение об ошибке, состояние сохраняется | → `AsPreview` |
| `AsPreview` | Название источника + 2–3 последних заголовка (fetch с таймаутом); «Подтвердить» / «Отмена» | Подтвердить → нет состояния, `/sources` |

**Настройки:** `StParam` (частота | время) → `StValue` → выход в меню.

Общие правила: любая команда (`/start`, `/sources`, …) сбрасывает текущее
состояние; ввод, не подходящий под шаг, — пояснение и повтор шага без
смены состояния.

### 1.4 Каталог источников

`bot/catalog_data.json`, записи:

```json
{
  "id": "reuters-metals",
  "title": "Reuters Metals",
  "kind": "rss",
  "url": "https://example.com/metals/rss",
  "topics": ["metals_fx"],
  "note": "опциональный комментарий"
}
```

- Теги тем: `metals_fx, usmarket, wsb, ipo_ai_bio, tech_ai, macro,
  geopolitics, crypto` (гипотеза H5 — соответствие `feeds.txt`, сверка).
- Подбор: темы опроса → фильтр по `topics`; сортировка по приоритету темы;
  ограничение сверху (~8 источников), чтобы первая сводка не была шумом;
  пользователь исключает лишние на шаге `ObSources`.
- Ноль выбранных тем → дефолтный набор по приоритетным темам (FR-02).

### 1.5 Контракт сводки (сообщения)

- `parse_mode=HTML`; все внешние строки через `html.escape` (D5).
- Структура: резюме-лид («что важно за период») → блоки по темам,
  пункты «заголовок — 1–2 предложения + ссылка» → футер с предупреждениями
  о деградированных источниках.
- Каждое сообщение ≤ 4000 символов; разбиение только по границам абзацев
  (D4).
- Пустая дельта → «Новых новостей с прошлой сводки нет.» (D7).
- Mock (нет `LLM_API_KEY`): буллеты «заголовок — ссылка» + пометка (mock).

### 1.6 Промпт LLM (требования к генерации)

Русский язык; тон личного ассистента; каждый пункт обязан содержать ссылку
из исходных материалов (выдумывать ссылки запрещено); глубина тем по
приоритетам FR-02 (драгметаллы/USD/US-рынок/идеи/IPO-AI-биотех/AI-модели —
глубоко; макро — кратко; геополитика — только направление; крипта — очень
кратко); суммарный лимит ~3500 символов до разбиения.

## 2. Расписание и catch-up

- Слоты: `users.send_times` (P0: 1–2 шт., локальное время пользователя,
  конвертация по `tz_offset_min`; хранение UTC — D18).
- Цикл планировщика (тик ~30 с): вычислить следующий слот, уснуть до него;
  на слоте: собрать включённые источники → построить дельту от
  `last_sent_at` → LLM/mock → отправка → транзакция (digests +
  `last_sent_at`).
- Catch-up: пропущенные слоты не «навёрстываются» поштучно — просто
  проверяется `now ≥ следующий слот после last_sent_at`; если да, шлётся
  **одна** сводка за всё окно (FR-12). Точность слота ±1 мин (FR-10);
  длительный сбор/LLM допустимо перекрывает минуту — ок.
- Дублей нет: окно всегда от `last_sent_at`, отправка и сдвиг окна —
  одна транзакция.

## 3. Обработка ошибок и деградация

- Сбор: per-source `try/except`; ошибка → лог с URL и исключением
  (NFR-02); `N` последовательных неудач → `status='degraded'` +
  `status_msg`; предупреждение пользователю в `/sources` и футере сводки.
- `tgweb`: последовательные запросы с паузой 1–2 с между каналами;
  redirect на логин/403 → `degraded` с пояснением «превью канала закрыто».
- `twbridge`: недоступность после ретраев → `degraded`, предупреждение,
  не блокер (D3).
- `reddit`: обязательный User-Agent; 429 → backoff (NFR-04).
- LLM: таймаут 120 с, 3 попытки с экспоненциальным backoff; финальный
  отказ → mock-сводка с пометкой.
- Telegram: троттлинг отправок ~1 msg/s; при 429 — ожидание `retry_after`.
- HTTP (общее, `collectors/http.py`): connect 15 с / total 30 с; ретраи
  для сетевых ошибок и 5xx — 3 попытки, backoff 1→2→4 с.

## 4. Гипотезы переиспользования `pipeline/` (проверка на сверке)

| # | Гипотеза | Что проверяем | Если не подтвердится |
|---|---|---|---|
| H1 | HTTP-клиент с таймаутами/ретраями и RSS-парсер переиспользуются как библиотека | Наличие выделенного слоя, чистота функций без побочных эффектов | Пишем свой в `bot/collectors/`, `pipeline/` не трогаем |
| H2 | Нормализация элементов и хэш `url+title` совместимы по смыслу с `items` | Совпадение формулы хэша и полей | Своя формула, своя таблица — конфликтов нет (отдельная БД) |
| H3 | LLM-клиент (Z.ai GLM) и промпт сводки переиспользуются | Отделение клиента от промпта | Копируем клиент в `bot/llm.py`, промпт пишем новый (§1.6) |
| H4 | Разбивка ≤4000 и отправка в TG переиспользуются | Разбиение именно по абзацам | Свой `tgsend.py` |
| H5 | `feeds.txt` (`URL\|категория`) — затравка `catalog_data.json` | Формат строк, релевантность фидов | Каталог наполняем вручную из известных фидов |
| H6 | `news.db` допускает read-only импорт истории в `bot.db` | Совместимость полей url/title/date | Импорт отключён (D12), не блокер |
| H7 | Двухфазная схема launchd (подготовка 08:50/20:50 → отправка 09:00/21:00) **не** переиспользуется | — (решение принято) | — заменяется in-process планировщиком (D13) |

Правило: до подтверждения гипотез существующий `pipeline/` не правится;
новый код не импортирует `pipeline/*` вслепую.

## 5. Итерации разработки

Принцип: первая итерация — минимальный «тонкий срез» end-to-end, далее
наращивание. Каждая итерация завершается прогоном критериев AGENTS
(дубли/ссылки/отказ фида/mock/лимит 4000), записью в `LOG.md` (NFR-06).

### Итерация 1 — Скелет end-to-end (минимальный срез)

- Scope: `bot/` каркас (`config`, `db` со схемой §1.2, `tgsend`),
  aiogram polling; `/start` — простое приветствие (без опроса);
  `/digest` — сбор одного захардкоженного RSS → `items` → mock-сводка →
  отправка со split ≤4000. Ручной запуск `python3 -m bot`.
- FR: FR-13 (частично: ссылки, split), FR-14 (частично: две команды),
  NFR-01, NFR-03, NFR-05.
- Готово, когда: с пустым `.env` бот стартует и `/digest` выводит
  mock-сводку (stdout); с TG-токеном — присылает её в чат; повторный
  `/digest` не увеличивает `items` повторами.
- Зависимости: —.

### Итерация 2 — Онбординг, каталог, повторный опрос

- Scope: FSM опроса, `catalog_data.json` + подбор, keyboards, сохранение
  `users`/`sources` (`origin='survey'`), режимы A/B, FSM-timeout sweeper.
- FR: FR-01, FR-02, FR-03; NFR-06.
- Готово, когда: сценарии 6.1–6.3 `requirements.md` проходят вручную;
  `/sources` показывает подобранный набор; таймаут 10 мин работает.
- Зависимости: 1.

### Итерация 3 — CRUD источников + свои RSS

- Scope: `handlers/sources`, мастер добавления (валидация, превью),
  удаление, вкл/выкл; полноценное главное меню и все команды.
- FR: FR-04, FR-05, FR-14 (полностью).
- Готово, когда: добавленный валидный RSS приносит элементы в `/digest`;
  невалидный URL — понятная ошибка, FSM не ломается.
- Зависимости: 2.

### Итерация 4 — Расписание, дельта, catch-up

- Scope: `scheduler.py`, `send_times`/`last_sent_at`, окно дельты,
  `handlers/settings`.
- FR: FR-10, FR-11, FR-12.
- Готово, когда: слот через 2 минуты → сводка в ±1 мин; окно = прошлой
  отправки (проверка по `digests`); останов бота на 2 слота → одна
  догоняющая сводка, `last_sent_at` сдвинут один раз.
- Зависимости: 2 (3 — желательно).

### Итерация 5 — LLM-сводка и живость UI

- Scope: `llm.py` (GLM + mock), промпт §1.6, `with_typing`,
  HTML-экранирование, футер деградации.
- FR: FR-13 (полностью), FR-15, FR-16; NFR-04.
- Готово, когда: с `LLM_API_KEY` — сводка стилем ассистента на русском,
  каждый пункт со ссылкой; без ключа — mock end-to-end; видно «печатает…»;
  заголовки с `<,&,#,_` не ломают отправку.
- Зависимости: 4.

### Итерация 6 — Новые типы источников

- Scope: коллекторы `html`, `tgweb`, `reddit`, `twbridge`; типоспецифичная
  валидация в мастере; статусы деградации.
- FR: FR-06, FR-07, FR-08, FR-09; NFR-02.
- Готово, когда: каждый тип добавляется и приносит элементы; выключенный
  мост → предупреждение и рабочий прогон; мёртвый URL → запись в логе с
  URL, прогон завершён.
- Зависимости: 3, 5.

### Итерация 7 — Продакшен под launchd

- Scope: launchd-агент на `python3 -m bot` (KeepAlive, автозапуск),
  логирование в `logs/`, обновление инструкций (остановка агента перед
  ручным запуском — D15), `.env.example`, финальный чек-лист NFR-01…07 +
  критериев AGENTS.
- FR: — (инфраструктура); NFR-01…07 — приёмка.
- Готово, когда: после перезагрузки Mac бот поднимается сам; ручные
  `bootout/bootstrap/kickstart` задокументированы; полный чек-лист зелёный.
- Зависимости: 6.

### Итерация 8 (P1) — Mini App

- Scope: `bot/webapp/` (минимальный веб-сервер на том же процессе),
  авторизация `initData`, CRUD-UI источников и настроек; fallback-кнопка в
  бот-интерфейс.
- FR: FR-17. Готово: CRUD через Mini App работает; при неработоспособном
  веб-пути кнопка ведёт в бот-меню.
- Зависимости: 7.

### Итерация 9 (P1) — Мультипользователи

- Scope: проверка изоляции per `chat_id` (схема готова с итерации 1),
  онбординг для каждого нового чата, per-user расписание.
- FR: FR-18. Готово: два тестовых чата — изолированные наборы и расписания.
- Зависимости: 7.

### Итерация 10 (P2) — «Сводка сейчас» + статистика

- Scope: кнопка с пересчётом `last_sent_at` (D10); `/stats` — счётчики
  элементов per источник.
- FR: FR-19, FR-20. Готово: после «сводки сейчас» плановая сводка не
  повторяет её; `/stats` сходится с БД.
- Зависимости: 7.

## 7. Риски

| # | Риск | Триггер (как обнаруживаем) | План реакции |
|---|---|---|---|
| R1 | t.me/s блокирует запросы или у канала отключено превью | Рост 403/redirect на логин в логах | Источник → `degraded` с пояснением; паузы между запросами; предложить RSS-зеркало канала |
| R2 | RSS-мост Twitter нестабилен/умер | Таймауты/5xx после ретраев | By design деградация: предупреждение пользователю, прогон продолжается (D3) |
| R3 | LLM API недоступен/лимиты | 4xx/5xx после ретраев в логах | Fallback на mock-сводку с пометкой; расписание не пропускается |
| R4 | Конфликт getUpdates (409) при ручном запуске | `Conflict: terminated by other getUpdates` | Процедура из AGENTS: `bootout` агента перед ручным запуском, `bootstrap` после; задокументировать в итерации 7 |
| R5 | Блокировки SQLite (бот + ручные прогоны) | `database is locked` в логах | WAL, короткие транзакции, один пишущий процесс, `busy_timeout`; ручные CLI-прогоны — только при остановленном боте |
| R6 | Сон Mac в момент слота | `now - last_sent_at > периода` при пробуждении | Catch-up одной сводкой за всё окно (§2); дублей нет благодаря транзакционной фиксации |
| R7 | Breaking changes / несовместимость версий aiogram | Ошибки импорта/вызовов при обновлении | Версия зафиксирована в зависимостях; обновление — отдельным сознательным шагом |
| R8 | Хрупкость HTML-парсинга сайтов (редизайн) | 0 элементов от источника N прогонов подряд | `degraded` + предупреждение; пользователь заменяет/удаляет источник; парсер точечный per-сайт, без универсальной «магии» |
| R9 | Ошибки Telegram entities / превышение 4096 | `BadRequest: ... too long / can't parse entities` | Строгий `html.escape` всех внешних строк; split по абзацам ≤4000; тесты на спецсимволах (итерация 5) |
| R10 | Лимиты Telegram (429 при отправке) | 429 в логах | Троттлинг ~1 msg/s, ожидание `retry_after` |
| R11 | Reddit 429 без OAuth | 429 в логах | Обязательный User-Agent, backoff, сниженная частота; при стойких блокировках — `degraded` |
| R12 | Расползание scope / переусложнение | Итерация превышает scope, появляются «на будущее» абстракции | Возврат к karpathy-guidelines: минимальный диф, каждый элемент соответствует FR; откат лишнего |

## 8. Принципы исполнения

- Минимальный диф; никаких спекулятивных абстракций (коллекторы — функции,
  SQL — в `db.py`, без ORM и слоёв «про запас»).
- `pipeline/` не правится и не импортируется вслепую до фазы сверки (§4).
- Каждая итерация: прогон критериев AGENTS 1–5 + релевантных FR/NFR,
  запись в `LOG.md`.
- Коммиты и изменения launchd-агента — по факту итерации 7; до этого бот
  запускается вручную.

### П.2 Схема БД: дельта к §1.2

- `items`: без `in_digest`; `published` — ISO (нормализация
  `published_parsed` при сборе); UNIQUE `(source_id, url_hash)` остаётся.
- Новая таблица потребления окна (D26):

```sql
CREATE TABLE digest_items (
  digest_id INTEGER NOT NULL REFERENCES digests(id) ON DELETE CASCADE,
  item_id   INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  PRIMARY KEY (digest_id, item_id)
);
```

- `sources`: + `last_post_id INTEGER NOT NULL DEFAULT 0` (для `kind='tgweb'`,
  семантика `channel_subs` из продa).
- `chat_history` (+ переносится при миграции): `chat_id` добавляется к
  существующим полям role/text/created_at.
