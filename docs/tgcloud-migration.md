## 3. Что теряется без cron (главное)

Сбор по запросу означает: между сообщениями бот ничего не собирает. `t.me/s` отдаёт
последние ~20 постов (пагинация `?before=` ограничена 6 страницами — ~120 постов),
RSS — 10–50 записей. Канал/фид с высокой частотой (100+ постов в день) за неделю
простоя отдаст только хвост: **недельная сводка будет неполной для быстрых источников**.
Это не баг реализации, а свойство платформы; в сводке должно быть явно написано, за
какой интервал данных нет (промпт R2, «честность вместо тишины»).

## 4. Блокеры: нужны решения пользователя

1. **Лимит инвокации (не проверен — нужен `tgcloud login`).** Если он меньше времени
   мега-вызова (в проде `effort=max` давал 54.8k выходных токенов, это минуты), сводка
   физически не влезает в один вызов. Варианты: (A) резать сбор и LLM на партии с
   курсором в БД + внешний триггер; (B) внешний бесплатный cron — GitHub Actions
   `schedule:` в уже существующем репозитории (Mac и Pi не участвуют, публичный репо —
   минуты бесплатны); (C) снижать `effort` (против требования R4).
   Рекомендация: сначала замерить, затем (B) при нехватке лимита.
2. **Полные тексты (`enrich.py`/trafilatura).** Варианты: (A) свой экстрактор;
   (B) только `content:encoded`/`items.text` из фидов (дешевле, часть источников без
   полного текста); (C) отказаться от «ТЕКСТ:» и жить на «ВЫЖИМКА:».
   Рекомендация: (B) — минимальный код, покрывает большинство фидов, пробелы видны в сводке.
3. **Глубина недельного окна.** Варианты: (A) честная пометка пробелов (как в промпте);
   (B) при разрыве >3 дней досбор `t.me/s` до предела пагинации + пометка по RSS.
   Рекомендация: (B) — это то же (A), плюс максимум доступной глубины.
4. **Живой вызов LLM для проверки `effort=max`** (тратит токены) — разрешение нужно
   один раз, на этапе проверки контракта.
5. **Судьба Python-версии в репо.** Держим `bot/` до приёмки (путь отката, как в промпте)
   или переносим в `legacy/` сразу?

## 8. Привязка проекта к боту: схема файлов (проверено по исходникам CLI 0.2.0)

CLI резолвит токен в таком порядке и **никогда не спрашивает его посреди команды**:

1. переменная окружения `TGCLOUD_TOKEN` (для CI, на диск не пишется);
2. файл `.tgcloud/credentials` в корне проекта.

Формат файла — строгий JSON, ровно одно поле, права 600:

```json
{
  "token": "app<id>:<secret>"
}
```

`app<id>` — публичная часть (номер приложения), `<secret>` — секрет из BotFather →
ваш бот → Serverless → CLI Access → Access token. Токен **бота** (`<bot_id>:AA…`)
для CLI не подходит: это разные токены.

Файлы, которые нужны для рантайма (генерируются, в git не попадают):

| Файл | Откуда | Содержимое |
|---|---|---|
| `.tgcloud/credentials` | кладёт пользователь | `{"token": "app…"}` |
| `tgcloud/lib/secrets.js` | `node scripts/build-config.mjs` из `.env` | `allowedChatId`, `llmApiKey`, `llmBaseUrl`, `llmModel` |

Проверка без сети и без секретов в выводе: `npx tgcloud status` (офлайн, показывает
незадеплоенные модули и «Not linked to a bot yet», пока файла нет).

## 9. Замеренные лимиты рантайма (2026-10-19, практика `tgcloud run`)

Замеры сделаны на живом проекте (`app8766943850`), пробник удалён после измерения.

| Что мерили | Результат | Чем мерили |
|---|---|---|
| CPU на инвокацию | **≈ 3 с** → `✗ Terminated: CPU timer exceeded` | busy-loop 50…5000 мс: любой блокирующий цикл умирает ровно на 3.0 с |
| Стена (wall time) | **≈ 30 с** | HTTP-ответ длиной 27.1 с — ок; 34 с → `HTTP 500` от платформы |
| Один сетевой запрос | 10.4 с и 27.1 с — ок | `httpbin.org/delay/10`, `/drip?duration=30` |
| `setTimeout` / `setInterval` / `AbortSignal` | **отсутствуют** | `typeof` в изоляте: `undefined` |
| `res.body.getReader()` | **отсутствует** (TypeError) | потоковое чтение недоступно, только `res.text()` |
| Таймеры в `Date.now()` во время busy-loop | **замирают** (виртуальные часы идут только на I/O) | busy-loop с `Date.now()` уходит в вечный цикл |
| CPU на реальную работу | 4 мс (тривиальный вызов), 21 мс (insert+select), 35 мс (fetch) | пробник |
| БД | insert/select работают, схема применилась (8 таблиц) | `migrate --safe` + пробник |

### Следствие для архитектуры (главное)

Мега-вызов дайджеста на `effort=max` в проде занимает **минуты** (iter-20: 54.8k выходных
токенов только на thinking), а вызов живёт **30 секунд**. Значит:

1. **Один вызов ≠ одна сводка за неделю.** Работу делим на шаги, каждый ≤ ~25 с:
   сбор партии источников → map-стадия (выжимки по партиям) → синтез.
2. Состояние шагов живёт в БД (таблица `jobs`, курсор), поэтому шаг можно продолжить
   следующим вызовом — своего «продолжения по таймеру» платформа не даёт.
3. CPU-бюджет 3 с запрещает тяжёлый разбор «все источники за раз»: парсинг идёт
   партиями, а не одним проходом по 100 фидам.
4. Живой прогресс «думаю…» через стрим недоступен (нет `getReader`), поэтому статус
   обновляется между шагами, а не токенами.

### Замер боевого мега-вызова (2026-10-19, локально, Node + DeepSeek)

Реальный вход из 13 источников (7 RSS + 1 канал, 53 пункта, 25 233 символа):

| Показатель | Значение |
|---|---|
| Сбор источников | 0.7 с (55 пунктов) |
| Первый байт ответа LLM | 0.8 с |
| **Вся генерация** | **264.5 с (4 мин 25 с)** |
| Выход | 12 779 символов текста, 63 487 output-токенов (thinking + текст) |
| `stop_reason` | `end_turn` — в 96k уложились, обрезки нет |
| Качество | лид по делу, разделы на месте, ссылки-эмодзи есть |

Итог: боевая сводка = **9× лимита вызова (30 с)**. Значит LLM-часть физически
не может жить внутри инвокации платформы, при этом качество (`effort=max`) —
ровно то, что просил пользователь. Дешёвые шаги (сбор, отбор, запись результата)
укладываются в платформу с запасом: 0.7 с на сбор, миллисекунды на запись.

### Открытый риск

Три требования сходятся в одну точку: «полный поток за неделю» + «effort=max» +
«30 с на вызов». На платформе это несовместимо без внешнего исполнителя тяжёлой
части. Варианты (решение принимает пользователь):
- (A) внешний бесплатный воркер (GitHub Actions `workflow_dispatch`, запуск по кнопке
  от бота) делает сбор и LLM без лимитов и пишет результат в БД платформы;
- (B) остаёмся в 30 с: много мелких LLM-вызовов на `effort=high`, сводка короче и
  дешевле по качеству — против требования «максимальное мышление»;
- (C) гибрид: map-стадия на `effort=high` внутри платформы, синтез — на воркере.

## 10. Куда вставлять токены (три разных места, не перепутать)

Диагностика 2026-10-19: CLI-токен платформы живой (`/manage/get` → ok), но её
`/manage/webhook` отвечает `WEBHOOK_GET_FAILED: Unauthorized` — значит **токен бота
на стороне платформы отозван**. Локально `getMe` тем же токеном из `.env` даёт
`401 Unauthorized` — то же самое. Проверка одной командой: `node scripts/verify-link.mjs`.

| Место | Что кладём | Формат | Зачем |
|---|---|---|---|
| BotFather → бот → **API Token** | новый токен от `@cumulativenewsbot` (Revoke → новый) | `1234567890:AA…` | Bot API: доставка сообщений, вебхук |
| BotFather → бот → **Serverless** → приложение `app8766943850` | тот же новый токен бота (если у приложения есть поле/кнопка перепривязки; иначе — пересоздать приложение) | тот же | платформа проксирует Bot API **своим** токеном бота |
| `.secrets/bot-token.txt` (локально, 600, в `.gitignore`) | тот же новый токен | одна строка | проверка живучести, ручной вебхук, откат на Python-версию |
| `.tgcloud/credentials` (локально, 600, в `.gitignore`) | CLI Access token **платформы** | `app<id>:<secret>` | `push` / `migrate` / `run` |

Токен бота и CLI-токен — **разные**; подставлять один вместо другого нельзя
(CLI проверяет формат `^app\d+:[A-Za-z0-9_-]+$`).

Если Serverless-приложение придётся пересоздать: данных на платформе ещё нет,
потери нулевые — новая пара `app<id>:<secret>` кладётся в `.tgcloud/credentials`,
дальше `npm run config` → `npx tgcloud push` → `npx tgcloud migrate --safe`.

## 11. Как это работает сейчас (финал, 2026-10-19)

Один вызов платформы на сообщение, без внешних исполнителей:

```
Telegram → handlers/message.js  (лимит вызова ~30 с, CPU ~3 с)
  ├─ гейт, интенты, retention (≤300 строк)
  ├─ сбор БЫСТРЫХ источников (rss/twitter, ≤12 за вызов, дедлайн 5 с, без ретраев)
  ├─ отбор: ≤25 пунктов / 45k символов, per-source 4, анти-дедуп, окно 7 дней
  ├─ LLM: thinking ВЫКЛ, max_tokens 3000            → ~10-13 с
  ├─ отправка чанками ≤4000 (валидный HTML, фолбэк на текст) → запись в БД
  └─ ПОСЛЕ сводки: один МЕДЛЕННЫЙ источник (канал/сайт) в остаток бюджета —
     его пункты попадут в следующую сводку
```

Замеры живыми вызовами: сводка 7–13 с, полный вызов 12–22 с (медленный источник
после отправки, ограничен 6 с). Режим «мало времени» (остаток < 20 с) режет вход
до 10 пунктов и выход до 3000 токенов — короткая сводка лучше тишины.

Почему так, а не иначе (замеры):
- `thinking` вкл. + `effort=low` + 3500 токенов → **0 символов** (мышление съело бюджет);
- `effort=high` + 10000 токенов → 47.5 с (не влезает в 30 с);
- `thinking` выкл. + 4000 токенов → 17 с, 9.4k символов, `end_turn`.
- В изоляте НЕТ: `setTimeout`, `res.body.getReader`, конструктора `URL` — последнее
  ломало html-парсер (все ссылки отбрасывались, источники падали с PARSE).

Медленные источники (каналы через RSS-зеркало, html-страницы) намеренно вынесены
за пределы сводки: канал при 429 отдаёт ответ через 12 с и съедал бюджет LLM.

## 11b. Как это работало с воркером (историческое)

```
Telegram ──update──> платформа Serverless ──> handlers/message.js
                                              │ гейт (fail-closed), интенты
                                              ├─ «сводка» → jobs + workflow_dispatch ──> GitHub Actions
                                              │                                            │ collect → select → DeepSeek effort=max
                                              │                                            │ Bot API (свой токен) → ingest
                                              └─ вопрос по теме → LLM (service, без thinking) → Bot API
```

Почему так: замер дал 264 с на мега-вызов при лимите инвокации 30 с (§9). Поэтому тяжёлая
часть — на бесплатном воркере, а платформа отвечает мгновенно.

| Шаг | Где | Время (замер) |
|---|---|---|
| Приём сообщения, интенты, задача в БД, запуск воркера | платформа | 1.5 с |
| Сбор rss-партии | платформа | 7.5 с (7 источников) |
| Сбор tgweb-партии (через RSS-зеркало) | платформа | до 23 с (4 канала) |
| Отбор в промпт | платформа | 1.7 с (124 пункта, 83 143 символа) |
| Генерация сводки `effort=max` | воркер (GH Actions) | 217–265 с |
| Отправка 6 сообщений + запись в БД | воркер + платформа | 2 с |

Работает и проверено живыми прогонами:
- сводка за период: 124 пункта → 6 сообщений в Telegram, `digest_items` записаны;
- повторный запуск: 0 непрочитанных (окно и `last_sent_at` двигаются корректно);
- вопрос по теме: «а что по золоту?» → ответ по накопленной ленте со ссылками;
- кнопка от бота: `«сводка»` → `workflow_dispatch` → воркер стартовал;
- Bot API напрямую: `getMe` из платформы отдаёт `cumulativenewsbot` (обход мёртвого токена платформы).

Единственное, что зависит от платформы: **приём апдейтов** (вебхук). Пока приложение в
BotFather не получит новый токен бота, вебхук не выставлен (`url: ""`), и сообщения
пользователя до бота не доходят. Всё остальное готово.

## 12. Приём апдейтов: только вебхук платформы

Внешние исполнители удалены по требованию пользователя (2026-10-19): GitHub-воркер,
поллер и их workflow/эндпоинты больше не существуют. Апдейты приходят **только** через
вебхук, который ставит сама платформа.

Пока приложение в BotFather не получило рабочий токен бота, вебхук не выставлен
(`/manage/webhook` → `WEBHOOK_GET_FAILED: Unauthorized`) и бот не получает сообщения.
Свой секрет вебхука платформы неизвестен (`POST app<id>.tgcloud.ai/api/webhook` → 401),
поэтому подставить его вручную нельзя: нужен именно рабочий токен на стороне приложения.

Историческое (снято): поллер long-polling-ом терял апдейты из-за `offset:-1` на старте;
cron GitHub на этом репозитории не срабатывал вовсе.
