# pi-telegram-bridge

Репозиторий: `https://github.com/livbig/pi-telegram-bridge`.

Мост между Telegram и сессиями [pi](https://github.com/earendil-works/pi): список сессий,
продолжение любой из них, работа **нескольких чатов параллельно**, все команды pi и живой стрим
ответа в одном сообщении.

Один процесс-бот + по одному дочернему `pi --mode rpc` на каждую используемую сессию
(поднимаются лениво, гаснут по бездействию), состояние на диске.

**Состояние на сейчас** — [`docs/PROJECT-STATE.md`](docs/PROJECT-STATE.md): запущен ли мост,
что проверено, следующий шаг. Правила — [`AGENTS.md`](AGENTS.md), решения — `docs/DECISIONS.md`.

```
Telegram ⇄ grammY (long polling) ⇄ bridge.js ⇄ session-pool.js ⇄ pi --mode rpc  (сессия A)
                                     ↕            │
                        state.json (чат → сессия)  └──────────────────────→ pi --mode rpc  (сессия B)
                                     ↕
                     SessionManager.listAll() — список сессий с диска
```

## Что умеет

| Команда | Действие |
|---|---|
| `/menu` | меню: 📁 Проекты, 🆕 Новая смета, 🧾 Клиенты, ❓ Помощь |
| `/sessions` | список сессий (id, имя, cwd, время) с кнопками выбора |
| `/open <номер\|id\|имя>` | открыть/продолжить любую сессию |
| `/continue` | последняя сессия этого каталога |
| `/new` | новая сессия |
| `/name <текст>` | имя текущей сессии |
| `/status` | модель, сессия, сообщения, токены, стоимость, контекст |
| `/model [provider/id]` | выбрать модель (без аргумента — список) |
| `/thinking <off…max>` | уровень рассуждений |
| `/compact [инструкции]` | сжать контекст |
| `/commands` | команды расширений, шаблоны и скиллы pi |
| `/stop` | прервать прогон (очередь очищается) |
| `/help`, `/chatid` | справка, id чата и пользователя |

Любой другой текст уходит промптом в сессию этого чата. Команды из `/commands`
(`/goal`, `/skill:ponytail`, шаблоны) запускаются как есть. Голосовые и аудио распознаются
через OpenRouter STT и уходят в сессию с префиксом `[голос 3:42] `. Фото (самый крупный размер)
и документы pdf/docx/xlsx/txt/csv/json/zip до 20 МБ скачиваются в `/srv/assistant/data/inbox/`:
фото уходит в pi изображением (или текстом `[фото: путь]`, если RPC не умеет картинки), документ —
текстом `[документ: путь]` с просьбой разобрать его инструментами. Стикеры и видео вежливо
отклоняются. В группах бот реагирует только на
`@имя_бота` или ответ на своё сообщение (`PI_TG_REQUIRE_MENTION`), команды работают всегда;
в личке — всё. Во время прогона новые сообщения
встают в очередь в рамках своей сессии — прогон в другом чате идёт параллельно.
Ход виден в реальном времени: над ответом — две строки курсивом, «что происходит» (смешная
фраза о процессе, меняющаяся каждые 4 с, ⚙ запущенный инструмент или заметка о сжатии/повторе)
и «сколько»: 👾 📡 🐴 · токены · контекст · стоимость · баланс API. Текст мыслей модели в чат
не попадает. Цифры обновляются по ходу (запрос `get_session_stats` раз в 4 с). Дальше — растущий
текст в **одном** сообщении и финальный ответ с разметкой.

`/sessions` присылает короткий заголовок («Список сессий (59):») и кнопки — по одной на сессию,
подпись кнопки это превью (первые слова, как в пикере `/resume` у pi). Метка `▸` — сессия этого
чата, `●` — процесс pi для неё уже поднят. Сессии за пределами первой страницы — текстом:
`/open <номер|id|имя>`.

**Меню и проекты без Mini App.** `/start`, `/menu` или слово «меню» присылают «Чем помочь?»
с кнопками `📁 Проекты`, `🆕 Новая смета`, `🧾 Клиенты`, `❓ Помощь`. Проекты и сметы читаются
с локального HTTP API на том же Pi (`MINIAPP_API_URL`, по умолчанию `http://127.0.0.1:8088`,
токен — `MINIAPP_SERVICE_TOKEN`), Mini App и HTTPS-туннель для этого не нужны. Список объектов —
кнопками по 8 на страницу (`⬅️`/`➡️`), объект — карточкой (заказчик, последняя версия, итог),
версии — кнопками, версия — сводкой строк, итога, скидки 5 % за наличные и суммы к оплате.
PDF приходит документом через `sendDocument`. Долгие запросы показывают «⏳ собираю…» и правят
это же сообщение; ответы API кешируются на 30 с, ошибка видна текстом («не смог получить
проекты: …»). Пункты «Новая смета» и «Клиенты» пока отвечают тостом «недоступно»: Mini App
отключён, а отдельных API для них нет.

Ответ рендерится **Rich Messages** (Bot API 10.1+): Telegram сам разбирает markdown, поэтому
таблицы, списки и блоки кода выглядят как в pi, а в клиенте на время генерации появляется
**кнопка «стоп»** (нажатие прерывает прогон). Markdown-заголовки мост перед отправкой превращает
в жирный текст: Telegram рисует `# заголовок` крупным шрифтом с засечками, который в чате смотрится
чужеродно (владелец: «заголовки шрифтом с serifs, а базовый текст нет»); в код-блоках решётку не трогаем.
Если методы rich недоступны, мост переходит на классический путь: черновик `sendMessageDraft` →
`editMessageText` → финальный `sendMessage` с разметкой, собранной самим мостом. Сбой rich не
выключает его навсегда: после ошибки N сообщений идут классикой, затем попытка повторяется
(в логе — `rich-сообщения не сработали…`). `PI_TG_RICH=off` — принудительно только классика.

Длинные ответы режутся по разметке, а не по символам: таблица разбивается по строкам, в каждом
следующем сообщении повторяется шапка; HTML-таблицы в ответах команд так же остаются таблицами.

**Файлы от агента.** Строка `[file:/srv/assistant/data/outbox/смета.pdf]` в ответе пользователю
не показывается: файл уходит через `sendDocument`, а короткий текст перед маркером становится
подписью. Разрешены только пути внутри `/srv/assistant/data/outbox` и `/srv/assistant/data/inbox`
(меняется через `PI_TG_DATA_DIR`), файл — не больше 50 МБ; иначе в чат приходит текст с ошибкой.

**PDF одноразовый.** Документ сметы хранится только лёгким (`<id>/smeta.csv`, `<id>/estimate.json`):
после успешной отправки в чат файл сразу удаляется, а если отправка не удалась — живёт до уборки
(раз в час: `*.pdf` старше часа и опустевшие каталоги версий, с записью в лог сколько удалено).

## Установка с нуля

```bash
# 1. зависимости
cd self/pi-telegram-bridge
npm install

# 2. токен бота: @BotFather → /newbot → скопировать токен
# канонический .env — вне репозитория; в проекте на него симлинк
ln -s ~/.config/ai/env/pi-telegram-bridge.env .env   # если симлинка ещё нет
$EDITOR ~/.config/ai/env/pi-telegram-bridge.env      # PI_TG_BOT_TOKEN=123456:AA...

# 3. запуск
npm start
```

Из чата с ботом отправьте `/start` — бот спарится с вашим аккаунтом и запомнит его
(дальше сообщения от других аккаунтов игнорируются). Токен не пишется ни в состояние,
ни в логи — в выводе он маскируется.

**Если ботом уже пользовались через `pi-telegram` (тот же репозиторий badlogic).**
Спаренный пользователь и offset `getUpdates` переносятся автоматически из
`~/.pi/agent/telegram.json` — заново спариваться не нужно. Обязательно выключите старый мост,
иначе два процесса будут драться за `getUpdates` (в логах будет `409 … terminated by other
getUpdates`): в той сессии pi, где он подключён, выполните `/telegram-disconnect`, а само
расширение лучше убрать — `pi remove git:github.com/badlogic/pi-telegram`.

Требования: Node 22+ (проверено на 24), установленный `pi` (`pi --version`).
`node_modules/@earendil-works/pi-coding-agent` из зависимостей используется и как SDK
(клиент RPC и список сессий), и как сам CLI для дочернего процесса.

### Запуск как pi-package (необязательно)

```bash
pi install ./self/pi-telegram-bridge     # или путь/URL вашего форка
# в pi:
/telegram-bridge status                  # start | stop | status
```

В нижней панели pi появляется 📡, пока демон жив (проверка pid-файла раз в 5 секунд), и
исчезает, когда он остановлен. Порядок иконок задаётся ключом статуса: pi сортирует их по алфавиту,
поэтому свои ключи начинаются с цифры (`1-agent-skills` → 👾, `2-telegram-bridge` → 📡) и стоят
первыми; статусы чужих пакетов (`caffeinate`, `goal`, `ponytail`) идут дальше в своём алфавитном
порядке. Обёртка поднимает тот же демон отдельным процессом: бот управляет
сессиями, поэтому внутрь текущей сессии pi он не встраивается. Логи такого запуска — 
`~/.pi/agent/pi-telegram-bridge/bridge.log` (рядом с `bridge.pid`); тот же демон находит 📡 в
нижней панели по pid-файлу.

### Запуск на Raspberry Pi

Боевой вариант — Raspberry Pi 4 (4 ГБ), Debian 13, Node 22. Мост здесь единственный фронтенд:
бот, сессии pi и голос живут в одном процессе-демоне, поэтому память считаем по процессам.

1. **Node и pi.** Node 22+ в `PATH` (`node --version`), `pi --version` работает. Если systemd
   не видит `pi`, задайте `PI_TG_CLI_PATH` на `node_modules/@earendil-works/pi-coding-agent/dist/cli.js`.
2. **env-файл.** Токен и ключи — в `~/.config/ai/env/pi-telegram-bridge.env` (права `600`),
   в каталоге проекта — симлинк `.env`. Не храните токен в unit-файле.
3. **Память.** `NODE_OPTIONS=--max-old-space-size=512` ограничивает heap каждого Node-процесса
   (мост и дочерние `pi` наследуют его). Считаем так: мост ~100–200 МБ + 3 процесса `pi`
   по 200–400 МБ ≈ 1–1,5 ГБ; остальное оставляем системе и кэшу. `MemoryMax=3G` в cgroup —
   страховка от утечки, а не рабочий лимит. `PI_TG_MAX_PROCESSES=3` — жёсткий потолок,
   `PI_TG_MAX_IDLE_SESSIONS=1` и `PI_TG_IDLE_MS=300000` освобождают память после 5 минут тишины.
4. **systemd.** Логи — в journal, а не в `bridge.log`: journald сам ротирует и переживает рестарт.

```ini
[Unit]
Description=pi-telegram-bridge
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=pi
WorkingDirectory=/home/pi/pi-telegram-bridge
EnvironmentFile=/home/pi/.config/ai/env/pi-telegram-bridge.env
Environment=NODE_OPTIONS=--max-old-space-size=512
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Environment=PI_TG_IDLE_MS=300000
Environment=PI_TG_MAX_IDLE_SESSIONS=1
Environment=PI_TG_MAX_PROCESSES=3
Environment=PI_TG_TURN_MAX_MS=1200000
ExecStart=/usr/bin/node --env-file-if-exists=.env src/main.js
Restart=on-failure
RestartSec=5
MemoryMax=3G
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now pi-telegram-bridge
journalctl -u pi-telegram-bridge -f
```

`bridge.pid` рядом с `state.json` остаётся: по нему обёртка `/telegram-bridge status`
и pid-lock не дают поднять второй экземпляр (второй на том же токене получит `409`).
После правок `src/` перезапуск: `sudo systemctl restart pi-telegram-bridge`.

## Контекст сообщения, текстовые логи, heartbeat

**Контекст.** К каждому сообщению мост кладёт в окружение процесса pi `PI_CHAT_ID`, `PI_CHAT_TYPE`
(`private`/`group`/`supergroup`), `PI_USER_ID`, `PI_USER_NAME`, `PI_THREAD_ID` (тема форума).
Агент читает их из `process.env` — так инструмент `set_reminder` в ассистенте узнаёт, **где его попросили**
поставить напоминание (требование владельца 29.10.2026: «напоминалки там, где агента попросили»).
Значения ставятся при запуске процесса pi, то есть на сессию; сессию, открытую из двух чатов,
обслуживает процесс с контекстом того чата, который поднял его (`shortcut` в `src/session-pool.js`).

**Текстовые логи.** Дополнение к journald: в `<PI_TG_DATA_DIR>/logs/bridge-YYYY-MM-DD.txt` пишется
входящее сообщение (`вход: чат … · тип · имя (id) · первые 120 символов`), запуск инструмента,
отправка файла, стоимость и итог прогона, ошибки с трейсом. Секреты маскируются, телефон и почта
клиента в цитате сообщения заменяются на `[телефон]`/`[почта]` (`redactPii` в `src/mask.js`),
полный текст сообщения не пишется. Файлы старше 14 суток удаляются при первой записи дня.

**Одноразовые PDF.** Отправленный в чат PDF удаляется (`removeSentPdf` в `src/files.js`), но только если
файл не пересобрали, пока шла отправка (сравнивается `mtimeMs`): два прогона по одной версии сметы не
забирают документ друг у друга. Повторяющиеся маркеры `[file:…]` в одном ответе дедуплицируются.

**Heartbeat.** `bridge-heartbeat.json` в том же каталоге обновляется раз в минуту, пока мост жив.
По его возрасту сторож в ассистенте (`scripts/heartbeat.mjs`, systemd-таймер раз в 10 минут)
понимает, что мост молчит, и один раз пишет владельцу.

## Переменные окружения

Все — через `.env` (в `.gitignore`) или обычный экспорт. Полный список в `.env.example`.

| Переменная | Зачем |
|---|---|
| `PI_TG_BOT_TOKEN` | обязательно, токен от @BotFather |
| `PI_TG_ALLOWED_USER_ID` | кому разрешено; пусто — спаривание по первому `/start` |
| `PI_TG_CWD` | каталог по умолчанию для новых сессий (по умолчанию — cwd запуска) |
| `PI_TG_STATE_FILE` | где лежит состояние (по умолчанию `~/.pi/agent/pi-telegram-bridge/state.json`) |
| `PI_TG_DATA_DIR` | каталог файлов ассистента (`/srv/assistant/data`): `outbox` для отправки, `inbox` для принятых |
| `PI_TG_LOG_DIR` | каталог текстовых логов (`<PI_TG_DATA_DIR>/logs`): `bridge-YYYY-MM-DD.txt`, `bridge-heartbeat.json` |
| `PI_TG_API_ROOT` | корень Bot API (`https://api.telegram.org`); локальный сервер — для e2e-тестов |
| `PI_TG_CLI_PATH` | путь к `dist/cli.js` pi, если автопоиск не сработал |
| `PI_TG_PI_ARGS` | доп. флаги дочернего pi, например `--approve` для доверия проекту; пусто — все встроенные инструменты (`bash`, `edit`, `write`, MCP) доступны |
| `PI_TG_DRAFT` | `auto` (по умолчанию) или `off` — выключить поток драфтов |
| `PI_TG_RICH` | `auto` (по умолчанию) — Rich Messages с markdown и кнопкой «стоп»; `off` — только классический путь |
| `PI_TG_THREADS` | темы форума в одну сессию уже сведены всегда: сессия — на чат (`dm:<userId>` / `group:<chatId>`), тема её не меняет. Параметр остался для ключей меню и списков (`separate` по умолчанию) |
| `PI_TG_IDLE_MS` | сколько простаивает процесс pi, прежде чем его погасить (1800000) |
| `PI_TG_MAX_IDLE_SESSIONS` | сколько бездействующих процессов держать (3) |
| `PI_TG_MAX_PROCESSES` | жёсткий потолок одновременных процессов pi (4; на Pi — 3) |
| `PI_TG_TIMEOUT_MS` | через сколько тишины pi напомнить в чате (900000) |
| `PI_TG_TURN_MAX_MS` | абсолютный потолок хода, мс (1200000 = 20 минут) |
| `PI_TG_TURN_MAX_COST_USD` | потолок стоимости одного прогона, $ (2): перебор останавливает прогон |
| `PI_TG_REQUIRE_MENTION` | в группах только `@бот`/reply (true); `false` — отвечать на всё |
| `OPENROUTER_API_KEY` | ключ OpenRouter для распознавания голоса |
| `STT_MODEL` | модель STT (`openai/whisper-large-v3`) |
| `STT_BASE_URL` | база OpenRouter API (`https://openrouter.ai/api/v1`) |
| `STT_LANGUAGE` | язык распознавания (`ru`) |
| `MINIAPP_API_URL` | локальный API ассистента для меню/проектов (`http://127.0.0.1:8088`) |
| `MINIAPP_SERVICE_TOKEN` | сервисный токен этого API (заголовок `x-service-token`) |
| `PI_TG_LOG` | `debug`/`info`/`warn`/`error`/`silent` |

## Проверки

```bash
npm test          # 214 тестов (в т. ч. контекст сообщения, текстовый лог, heartbeat): разметка, чанки, троттлинг, состояние, поиск сессий, пул процессов,
                  # маппинг команд, живое сообщение, watchdog, голос/STT, pid-lock, обёртка pi-package,
                  # меню/проекты и API ассистента, end-to-end мост с поддельным Bot API
npm run e2e       # сквозной путь (медленный, ~5 с): апдейт Telegram → мост → настоящий pi
                  # с инструментами ассистента → PDF/сообщение → фейковый Bot API. Запускать перед деплоем
npm run smoke     # реальный pi: get_state, get_commands, список сессий, запуск на конкретной сессии
npm run smoke -- --prompt "ответь одним словом: ок"   # + настоящий прогон (тратит токены)
npm run rehearse -- "напиши список из 120 строк"      # боевой путь целиком: модель → стрим → чат
```

`npm run e2e` — единственная проверка, которая проходит путь целиком: настоящий процесс `pi`
с инструментами ассистента (`document_build`, `estimate_*`, `set_reminder`), настоящий PDF и
настоящий `sendDocument`. Подменены два внешних сервиса и только они: Bot API (локальный HTTP
на 127.0.0.1: `getMe`/`getUpdates`/`sendMessage`/`sendDocument`/`getFile`, записи о том, что ушло
в чат) и поставщик модели/STT (детерминированные ответы, никакой сети). Сценарии: смета с
документом и таблицей, голосовое с расшифровкой, напоминание в группу, отказная ветка
самопроверки PDF, смета без телефона заказчика. Нужен каталог ассистента рядом
(`../../perimetr/assistant`, иначе `E2E_ASSISTANT_DIR`); без него набор пропускается.
Перед деплоем, вместе с `npm test`: `npm test && npm run e2e`.

`npm run rehearse` отправляет реальный ответ модели в спаренный чат тем же кодом, что и бот
(живое сообщение, rich-разметка, разбивка), — так проверяется всё, кроме приёма сообщений Telegram.

Ручной сценарий в реальном Telegram (нужен токен):

1. `/sessions` → видно сессии с id, cwd и временем.
2. Кнопка с превью сессии или `/open <номер>` → «Подключил сессию…», затем вопрос — ответ в неё.
3. Перезапустите бота (`Ctrl+C`, `npm start`) и напишите снова: выбор сессии сохранён.
   Второй чат (или тема форума) — своя сессия, работают одновременно.
4. `/status` → таблица: скиллы значками (👾 agent-skills, 📡 мост, 🐴 ponytail — значок есть,
   значит включено), модель, токены, контекст, баланс API; `/model <provider/id>` → модель сменилась.
5. Попросите длинный ответ (>4096) → приходит несколькими сообщениями, разметка цела.
6. `/нетакой` → «Не знаю команду…» с подсказками.
7. Долгий прогон → `/stop` → «⏹ Прерываю». Либо кнопка «стоп» в самом сообщении Telegram.
8. Тот же длинный ответ: markdown (таблицы, код) отрендерен — значит rich работает; если видно
   звёздочки и решётки — поставьте `PI_TG_RICH=off` (или скажите, если фолбэк не сработал).

## Ограничения

- **Меню проектов** ходит в локальный API и не поднимает процесс pi. Если API лежит или токен
  не совпал, в чате будет ошибка текстом, а не тишина; данные кешируются на 30 с. Кнопки
  «Новая смета» и «Клиенты» пока не подключены — для них нет API, Mini App отключён.
- **Один процесс pi на сессию.** Два чата в одной сессии делят один процесс и одну очередь
  (это защищает файл сессии от параллельной записи), разные сессии работают параллельно.
  Не держите ту же сессию открытой в терминале — два писателя в один `.jsonl` ломают историю.
  Число процессов ограничено `PI_TG_MAX_PROCESSES` (по умолчанию 4): сверх него в чат уходит
  «занято N сессий, попробуй позже или /stop», новый процесс не поднимается.
- Бездействующие процессы (`PI_TG_IDLE_MS`, по умолчанию 30 мин) гасятся; сверх
  `PI_TG_MAX_IDLE_SESSIONS` самые старые вытесняются. Первое сообщение после паузы ждёт подъём
  процесса (секунда-две).
- **Зависший pi не блокирует чат.** Если `/stop` не получил ответ за 10 секунд, ход закрывается
  ошибкой, процесс гасится, следующее сообщение поднимает свежий. Тишина дольше
  `PI_TG_TIMEOUT_MS` даёт заметку в живом сообщении, абсолютный потолок `PI_TG_TURN_MAX_MS`
  (20 минут) прерывает ход и тоже гасит процесс.
- **Потолок стоимости прогона — $2** (`PI_TG_TURN_MAX_COST_USD`). Расход берётся из pi
  (`getSessionStats().cost`: разница с расходом до хода), проверяется на каждом событии конца
  ответа и раз в 4 с. Перебор — прогон прерывается, процесс гасится, в чат уходит
  «остановил себя: прогон стоил больше $2 (факт $…)», факт — в лог. Проверка механики:
  `PI_TG_TURN_MAX_COST_USD=0.0001 node scripts/live-cost-limit.js` (живой pi, настоящий расход).
- **Одна сессия на чат.** Ключ привязки — `dm:<userId>` для лички и `group:<chatId>` для группы;
  тема форума сессию не меняет. Пока файл сессии на диске, он переиспользуется всегда — после
  рестарта моста и после компакции (новая привязка пишется в `state.json` и в лог). Новый файл
  появляется только если прежний пропал (лог: `файл сессии … пропал`); тогда же возможен и `/new`.
  Старые файлы сводятся к трём скриптом `scripts/migrate-sessions.js` (архив — в
  `~/.pi/agent/sessions-archive/<дата>/`, не удаление).
- **Новая сессия (`/new`) создаётся в `PI_TG_CWD`** — открыть новую сессию в другом каталоге из
  чата нельзя (выберите существующую через `/sessions`).
- **Форматирование ответа.** Rich-путь (`sendRichMessage`) — основной: markdown уходит как есть,
  таблицы рисует Telegram. Отказ ЧЕРНОВИКА (в группах Telegram отвечает `TEXTDRAFT_PEER_INVALID`)
  больше не отключает rich-сообщения: живая строка идёт классикой, финал остаётся rich. Если rich
  недоступен, классический путь конвертирует GFM в HTML: таблица становится моноширинным `<pre>` с
  шапкой и выровненными числами, `<`/`&` экранируются, нарезка по 4096 закрывает и заново открывает
  теги. Последний резерв — простой текст без разметки; сырой markdown (`**`, `| ---`, `###`) в чат не
  уходит никогда. Проверка того, что реально уйдёт в Bot API: `src/format-check.js` (им же пользуются
  тесты `markdown`/`chunk`/`live` и сценарий e2e «форматирование»).
- Не поддержаны: `/tree`, `/settings`, `/login`, `/logout`, `/share`, `/bug`, `/trust`,
  `/reload`, `/copy`, `/import`, подкоманды `pi install/config/auth/mcp`, флаги старта
  (`--api-key`, `--system-prompt`, `--tools`…). Встроенные команды pi снаружи недоступны
  (см. `docs/DECISIONS.md`, D5) — эти реализованы своими средствами.
- Голосовые и аудио принимаются до 10 минут и 20 МБ (больше Телеграм не отдаёт): Telegram-файл скачивается, OpenRouter STT
  возвращает текст, в сессию он уходит как `[голос 3:42] …`. Ошибка распознавания — сообщение
  в чат, а не тишина. Фото — до 20 МБ, документы — pdf/docx/xlsx/txt/csv/json/zip до 20 МБ;
  стикеры и видео не принимаются. Ошибка скачивания входящего файла видна в чате.
- Файлы от агента ограничены каталогами `outbox`/`inbox` и 50 МБ; маркер `[file:…]` в тексте
  ответа не показывается. Симлинк наружу не обходит проверку (путь сверяется после `realpath`).
  PDF после отправки удаляется; файлы других форматов остаются как раньше.
- В группах без `@бот` и без reply на сообщение бота мост молчит; команды (`/...`) работают
  всегда. Спаривание `/start` — только в личке.
- Диалоги расширений pi (`select`/`confirm`/`input`) не показываются: мост отвечает
  «отмена» и сообщает об этом в чат. Уведомления расширений (`notify`) приходят как сообщения;
  рутинные гасятся настройками самих расширений — у `pi-caffeinate` в `~/.pi/agent/pi-caffeinate.json`
  стоит `"quiet": true` (иначе каждый прогон присылает «Keeping computer awake»), у ponytail в
  `~/.config/ponytail/config.json` — `"quietStartup": true` (иначе на каждый старт сессии —
  «Ponytail loaded: full»).
- Для проектов с `.pi/`-ресурсами pi не может показать запрос доверия в неинтерактивном
  режиме. Если ресурсы не загрузились, добавьте `PI_TG_PI_ARGS=--approve` или сохраните
  решение через `/trust` в обычном pi.
- Разбивка длинного ответа не отслеживает блоки кода: ``` может разорваться между сообщениями.
- После падения дочернего pi мост перезапускает его при следующей команде; незавершённый ход
  теряется (в чат уходит сообщение об ошибке).

## Если не запускается

| Симптом | Что делать |
|---|---|
| `PI_TG_BOT_TOKEN не задан` | создайте `.env` из `.env.example` |
| `Не нашёл CLI pi` | задайте `PI_TG_CLI_PATH=.../node_modules/@earendil-works/pi-coding-agent/dist/cli.js` |
| `409 … terminated by other getUpdates` | тем же токеном опрашивает кто-то ещё: второй экземпляр моста (`ps ax \| grep src/main.js`) или старый pi-telegram (`/telegram-disconnect`). Оставить нужно ровно один |
| Бот молчит после `/start` | проверьте `PI_TG_ALLOWED_USER_ID`, логи с `PI_TG_LOG=debug` |
| Драфт не анимируется | клиент Telegram не поддерживает; мост сам перейдёт на правку сообщения |
| Сессия не восстанавливается | файл сессии удалён: `/sessions` и выберите другую |
| Бот ответил «процесс pi остановился» | дочерний pi умер (упал или убит снаружи) — мост закроет ход и поднимет сессию заново; причину смотрите в `bridge.log` (`pi_exit`, stderr) |
| `Мост уже запущен (pid …)` | pid-lock нашёл живой демон: остановите его `/telegram-bridge stop` или `kill <pid>`; второй экземпляр на том же токене даст `409` |
| «Голос не настроен» | задайте `OPENROUTER_API_KEY` в `.env` и перезапустите мост |
| «Не смог распознать голос» | STT вернул ошибку/пустой текст — в сообщении причина; пришлите текстом или короче 10 минут |

## Устройство репозитория

```
src/main.js      точка входа: конфиг, state, pi, бот, graceful shutdown
src/bridge.js    политика: авторизация, роутинг чат → сессия, команды, очередь, стрим, long polling
src/session-pool.js  по процессу pi на сессию: ленивый запуск, переиспользование, гашение по idle
src/status.js    форматирование ответов команд: таблицы rich-HTML для /status, /models, /commands
src/pi.js        RpcClient: запуск дочернего pi, ленивый перезапуск, JSONL для диалогов
src/legacy.js    перенос спаренного пользователя и offset из pi-telegram
src/live.js      живое сообщение: драфт → editMessageText → финальный sendMessage
src/files.js     входящие файлы в inbox, безопасная отправка из outbox/inbox, уборка одноразовых PDF
src/rich.js      предохранитель rich-сообщений: после сбоя повтор через N сообщений
src/sessions.js  список/поиск/формат сессий (SessionManager.listAll)
src/commands.js  разбор команд чата и маппинг на RPC pi (чистые функции)
src/markdown.js  GFM → Telegram HTML
src/chunk.js     разбивка под 4096: текст, markdown-таблицы, HTML-теги
src/throttle.js  троттлинг правок и coalescing
src/state.js     состояние на диске (атомарная запись)
src/config.js    env и маскирование секретов
extensions/      pi-package: /telegram-bridge start|stop|status
scripts/smoke.js ручная проверка связки с pi
test/e2e/        сквозные тесты: фейковый Bot API, фейковая модель, стенд ассистента
docs/            RESEARCH.md (первоисточники), DECISIONS.md (ADR и порядок фаз)
```

Проектные решения и ссылки на документацию pi: `docs/DECISIONS.md`.
