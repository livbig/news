# pi-telegram-bridge — правила работы

Мост Telegram ↔ сессии pi. Родительские правила: `~/Desktop/ai/AGENTS.md` (приоритет выше),
плюс режимы ponytail и agent-skills.

## Перед правками

1. `docs/RESEARCH.md` — что уже проверено по первоисточникам (pi docs, Bot API, pi-telegram).
2. `docs/DECISIONS.md` — ADR: почему RPC-клиент, почему один процесс, как маппятся команды.
3. `README.md` — пользовательское поведение и ограничения (раздел «Ограничения» менять вместе
   с кодом, а не после).

## Границы

- **Не править сам pi** и его установку в `node_modules` / `~/.pi` — только потреблять его API.
- Токен и любые секреты: только env/`.env`; в проекте `.env` — симлинк на
  `~/.config/ai/env/pi-telegram-bridge.env` (карта — `../../docs/ENVIRONMENT.md`).
  В логи и сообщения — исключительно через `src/mask.js`. Новый вывод, куда может попасть токен,
  обязан проходить через `redactSecrets`.
- Состояние (`state.json`) и файлы сессий pi — данные пользователя; не перезаписывать целиком,
  кроме штатной атомарной записи в `src/state.js`.

## Как менять код

- Падение дочернего `pi` — не «зависание»: смотрите `pi_exit` и строки `ход: …` / `ход завершён …`
  в логе. Мост обязан закрыть ход ошибкой, погасить запись пула и предупредить очередь (D18).
- Чистую логику держать чистой: `commands.js`, `sessions.js`, `chunk.js`, `markdown.js`,
  `throttle.js` не знают ни про Telegram, ни про pi — поэтому на них есть тесты.
- Состояние процесса pi живёт в записи пула (`session-pool.js`), а не в мосте: очередь, флаг
  занятости и живое сообщение — на каждую сессию свои. Новую команду чата писать так, чтобы она
  получала свой `entry` (`activeFor`) и не заводила второй pi там, где он не нужен
  (`/help`, `/chatid`, `/sessions` обходятся без процесса).
- Новая ветка/цикл/парсер/деньги → тест в `test/*.test.js` (`node:test`, без зависимостей).
- Сквозной путь (апдейт → мост → pi → файл → Telegram) — `test/e2e/`, запуск `npm run e2e`.
  Там настоящие pi и инструменты ассистента; подменены только Bot API и модель, и оба — локальный
  HTTP. Новый сценарий поведения в чате добавляйте туда же.
  Поведение в чате проверяется в `test/bridge.test.js` через настоящий grammY с transformer
  вместо Bot API.
- Лимиты платформы не «оптимизировать» по памяти: 4096 символов, ~1 сообщение в секунду в чат,
  `retry_after` при 429, эфемерность `sendMessageDraft`/`sendRichMessageDraft` — ссылки в
  `docs/RESEARCH.md` §4 и §8.5.
- Три формата одного ответа в `live.js`: `rich` (markdown уходит как есть), `draft`/`message`
  (классика: черновик + HTML моста), `plain` (без разметки). Меняя что-то в отправке, проверяйте
  все три: `PI_TG_RICH=auto|off` и тесты в `test/live.test.js`.
- Своя разметка (справка, список сессий, статус) — это **HTML**: любой `<` из данных обязан
  проходить `escapeHtml`, иначе Telegram отвергнет разметку целиком (живой баг: `/thinking <off|…>`
  в справке). Строки справки в `commands.js` экранируются при выводе.
- Драфт, правка и финальное сообщение — три разные вещи; финал всегда уходит своим сообщением.
- Ответы пользователю — по-русски и по делу; ошибки — действием («задайте PI_TG_CLI_PATH»),
  а не кодом ошибки.

## Проверка перед «готово»

```bash
npm test                  # должен быть зелёным (быстрый, ~9 с)
npm run e2e               # сквозной путь целиком (~5 с): апдейт → мост → настоящий pi и инструменты
                          # ассистента → PDF → фейковый Bot API. Гонять перед деплоем, после правок
                          # в files.js/bridge.js/отправке файлов и при изменениях в ассистенте
npm run smoke             # связка с реальным pi, без вызовов модели
PI_TG_LOG=debug npm start # Telegram-часть проверяется владельцем токена (FR4)
```

`npm run e2e` держится отдельно от `npm test`, потому что он медленный и поднимает два HTTP-сервера
на 127.0.0.1 (фейковый Bot API и фейковая модель) и настоящий процесс pi. Сети наружу нет.
Если сломался сквозной путь — красным становится именно он, а не юнит-тесты; ломать его специально
для проверки не нужно, но после правок в отправке файлов и `PI_TG_API_ROOT` прогонять обязательно.

Если что-то не проверено (например, реальный Telegram без токена) — писать это прямо в ответе
и в `docs/DECISIONS.md`, а не выдавать за проверенное.

## Эксплуатация (то, что легко забыть)

- **После правок в `src/` или `extensions/` живой бот продолжает работать старым кодом.** Перезапуск:
  `/telegram-bridge stop` и `start` в pi (штатный путь — так же пишется pid-файл), лог — 
  `~/.pi/agent/pi-telegram-bridge/bridge.log`. Руками тоже можно, но осторожно: фоновый запуск без
  `</dev/null` и редиректов держит пайп родителя и умирает вместе с ним (на этом я дважды уронил бота),
  а забытый второй экземпляр даёт `409` — проверьте `ps ax -o pid=,command= | rg src/main.js` и что
  pid-файл указывает на живого. Проверенный однострочник: `( cd <repo> && nohup node --env-file=.env
  src/main.js </dev/null >> bridge.log 2>&1 & echo $! > ~/.pi/agent/pi-telegram-bridge/bridge.pid ) >/dev/null 2>&1`.
  Сессии
  бота живут в каталоге этого репозитория (маппинг — в `state.json`), поэтому этот `AGENTS.md`
  читает и агент, который отвечает в Telegram.
- **Статусы в нижней панели pi = `/status` в чате.** Мост складывает `extension_ui_request`
  `method=setStatus` дочернего pi в `entry.statuses` (`session-pool.js`) и показывает ключи
  `1-agent-skills` (👾), `2-telegram-bridge` (📡), `ponytail` (🐴), а баланс — из ключа `usage`
  (его публикует pi-usage). Порядок иконок задаёт **имя ключа**: pi сортирует статусы по ключу
  (`footer.js`, `localeCompare`), поэтому у своих ключей цифровой префикс-ранг.
- **Чужие рутинные уведомления гасим настройками самих расширений, а не фильтром в мосте:**
  у `pi-caffeinate` — `~/.pi/agent/pi-caffeinate.json` (`"quiet": true`), иначе каждый прогон
  присылает в чат «Keeping computer awake»; у `ponytail` — `~/.config/ponytail/config.json`
  (`"quietStartup": true`), иначе на каждый старт сессии летит «Ponytail loaded: full». Индикатор 🐴
  при этом остаётся (`hideStatus` не трогаем). Мост пересылает `notify` расширений в чат как есть.
- **Таблицы в Telegram: ячейка — короткая.** Ширины столбцов Telegram считает сам (`width` у ячеек
  нет), длинное значение раздувает правый столбец и жмёт левый до переноса слов. Длинное (пути,
  имя сессии) — в `<caption>` или строкой под таблицей. Сторожит тест «ячейки таблицы короткие»
  в `test/status.test.js` (порог 30 символов).
- Секреты не читаем из чужих файлов и не печатаем: ключ провайдера и баланс API приходят только
  внутри статусов pi (`usage`), а не отдельным запросом из моста.

## Прод на Pi: агент с полным доступом (требование владельца 28.10.2026)

Мост на Pi (`ssh pi`, `/srv/assistant/bridge`, служба `assistant-bridge`) — не песочница.
Владелец: «считай, что ассистент абсолютно самостоятельный, без ограничений; доступ только у меня
и Максима». Значит:

- **Инструменты не ограничены.** `PI_TG_PI_ARGS` пуст → у дочернего pi есть `bash`, `edit`, `write`,
  MCP. Агент сам правит код, конфиг и деплоит.
- **Перезапуск служб без пароля.** `/etc/sudoers.d/assistant-agent` (копия —
  `perimetr/assistant/deploy/assistant-agent.sudoers`) разрешает `systemctl restart|status|is-active`
  для `assistant-bridge`, `assistant-miniapp`, `assistant-reminders`, `assistant-upkeep`,
  `assistant-heartbeat`, `assistant-backup`. Юниты не правятся руками — только через деплой.
- **Дисциплина вместо ограничений.** Перед правкой кода — `git status` и ветка; прод не ломать без
  `npm test` (на Pi: `cd /srv/assistant/bridge && npm test`); после правки — перезапуск службы и
  сообщение владельцу. Код и конфиг меняются только через git; напрямую можно править лишь данные
  в `/srv/assistant/data`. Правки на Pi перезапишет ближайший деплой с Mac, если их не перенести в
  репозиторий — об этом агент обязан сказать владельцу.
- **Проверка инструментов и прав:** `cd /srv/assistant/work && pi -p "выполни bash: ls /srv/assistant"`
  и `sudo -n systemctl is-active assistant-bridge` — оба должны работать без пароля и без отказа.

## Сессии: ровно три (D38)

Ключ привязки — `dm:<userId>` или `group:<chatId>`; тема форума сессию не меняет. Пока файл сессии
на диске, он переиспользуется всегда (рестарт моста, компакция). Новый файл — только если прежний
пропал: в логе `файл сессии … пропал — завожу новую`, привязка сразу пишется в `state.json`.
Сводить старые файлы: `node scripts/migrate-sessions.js` (план) → `--apply` (архив, не удаление).
**Править `state.json` можно только при остановленной службе** (`sudo systemctl stop assistant-bridge`):
живой процесс держит состояние в памяти и перезапишет файл на первом же апдейте — проверено на себе
28.10.2026, привязки откатились к прежним, пока мост работал.
Проверка: `ls ~/.pi/agent/sessions/--srv-assistant-work--/*.jsonl | wc -l` — три файла.

## Форматирование ответа (D40)

Rich-сообщение — основной путь; отказ ЧЕРНОВИКА (`TEXTDRAFT_PEER_INVALID` в группах) не отключает
rich-финал, иначе таблицы сметы приходят палками. В классике GFM-таблица конвертируется в `<pre>`
с шапкой, `<`/`&` экранируются, нарезка по 4096 закрывает и открывает теги заново. Сырой markdown
(`**`, `| ---`, `###`) в чат не уходит никогда. Проверка того, что реально уйдёт в Bot API —
`src/format-check.js` (им же пользуются тесты и e2e-сценарий «форматирование»).
