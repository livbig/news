## D1. Своя реализация поверх pi RPC, НЕ форк pi-telegram

**Решение.** Отдельный процесс-бот на Node (`node src/main.js`), который управляет одним
дочерним `pi --mode rpc` через экспортируемый `RpcClient`, а список сессий берёт через
`SessionManager.listAll()` из того же SDK. Из pi-telegram берём **приёмы** (драфт+фолбэк,
750 мс, `chunkParagraphs`, очередь, `stop`), код не копируем и не форкаем.

**Альтернативы.**

| Вариант | Почему отказ |
|---|---|
| A. Форк pi-telegram | Он **session-local** (README: «The Telegram bridge is session-local. Connect it only in the pi session that should own the bot») и живёт внутри сессии. Переключить собственную сессию из расширения нельзя: `session_before_switch` умеет только отменить switch. FR1/FR2 не закрываются конструктивно, а не «пока не доделали». |
| B. pi-package-расширение + SDK in-process | Нужно самому собрать `createAgentSessionServices` + `DefaultResourceLoader` + trust + MCP/codemode-фабрики (`examples/sdk/14-codemode-mcp.ts`) — свой дубль CLI-обвязки, больше кода и расхождение с реальным `pi`. Плюс список команд расширений снаружи не отдаётся (публичного `getCommands()` у `AgentSession` нет; `ExtensionRunner.getRegisteredCommands()` — внутренний), а в RPC есть готовый `get_commands`. |
| C. Своя реализация на `RpcClient` (выбрано) | Протокол документирован (`docs/rpc.md`), клиент типизирован и экспортируется из корня пакета (`dist/modes/rpc/rpc-client.d.ts`), `switch_session`/`new_session`/`get_commands`/`extension_ui_request` — первого класса. Поведение сессии = поведение настоящего `pi`. |

**Разрыв FR1–FR2 закрывается так:**
- FR1 — RPC списка сессий не имеет, поэтому список берём из SDK-API `SessionManager.listAll()`
  (`docs/sdk.md` → «List and open specific session», `examples/sdk/11-sessions.ts`), это API, а не
  ручной парсинг JSONL.
- FR2 — RPC-команда `switch_session{sessionPath}`; cwd и сервисы поднимаются из заголовка самой
  сессии (`agent-session-runtime.js:134-138` — `cwd: sessionManager.getCwd()`), т.е. продолжение
  сессии из другого каталога работает без нашей логики.

**Цена/риск.** Два процесса вместо одного: нужно резолвить путь к CLI и корректно переживать
падение/перезапуск дочернего процесса. Митигация: `PI_TG_CLI_PATH` в env, авто-рестарт по событию
выхода процесса, человеческая ошибка в чат.

## D2. Telegram: grammY + `@grammyjs/auto-retry`

**Решение.** Зависимости: `grammy`, `@grammyjs/auto-retry`, `@earendil-works/pi-coding-agent`.

**Обоснование каждой:**
- `grammy` — типизированный Bot API, long polling, `InlineKeyboard` для выбора сессии,
  `InputFile` для экспорта. **Проверено:** `sendMessageDraft(chat_id, draft_id, text, other?, signal?)`
  уже есть в типах grammy 1.46 (`node_modules/grammy/out/core/api.d.ts:494`).
- `@grammyjs/auto-retry` — ровно требуемый FR4 backoff: «wait for the specified number of seconds,
  Retry the request» по `retry_after` (grammY «Flood Limits»). Свой цикл ретраев не пишем.
- `@earendil-works/pi-coding-agent` — `RpcClient` + `SessionManager`.

**Отвергнуто:** голый `fetch` как в pi-telegram (это +200 строк своей обвязки: polling, ретраи,
multipart, клавиатуры и их callback-и), `telegraf` (то же, что grammY, но без auto-retry),
свой HTTP-транспорт поверх Bot API. Тесты — `node:test` (встроен в Node 24), тестовых зависимостей
нет.

## D3. Стриминг: драфт → фолбэк на editMessageText → финальный `sendMessage`

**Цитата (core.telegram.org, `sendMessageDraft`):**
> «the streamed draft is ephemeral and acts as a temporary 30-second preview - once the output is
> finalized, you **must** call `sendMessage` with the complete message to persist it in the user's chat»

**Решение.** Одно живое сообщение на ход:
`отправка "думаю…"` → драфты через `sendMessageDraft(chat_id, draft_id, text)` (draft_id
не меняется — «Changes to drafts with the same identifier are animated») → при первой ошибке
метода одноразовый флаг «драфт недоступен» и переход на `sendMessage` + `editMessageText` по тому
же `message_id` → на `agent_settled` финальный текст отдельным `sendMessage`, драфт гасится пустым
текстом. Троттлинг 750 мс на чат, «думаю…» ещё и через плейсхолдер драфта (пустой `text` =
«Thinking…» по документации).
Источник дельт — `message_update` / `assistantMessageEvent.text_delta`; граница — `agent_settled`
(`docs/rpc.md`: «Wait for `agent_settled` when the client needs to know Pi will not continue
automatically»), `text_end`/`message_end` перекрывают буфер.

**429.** Отдаётся `auto-retry`; дополнительно свои правки не чаще 1/сек на чат (`retry_after`
тоже уважается). Ошибки правок не роняют ход: последний текст всё равно уйдёт финальным
`sendMessage`.

**Markdown.** `parse_mode: "HTML"` + свой конвертер GFM→Telegram-HTML (fences → `<pre>`,
inline → `<code>`, bold/italic/link, экранирование `&<>` — ~60 строк с тестом). При 400
`can't parse entities` — повтор того же сообщения без `parse_mode`. MarkdownV2 отвергнут: требует
экранировать ~18 символов в уже готовом тексте агента, т.е. ломает форматирование.
**Отложено (см. «Открытые вопросы»):** Rich Messages (`sendRichMessage(Draft)`, Bot API 10.1+) с
нативным markdown — не берём, пока нет подтверждения поддержки клиентами.

## D4. ~~Модель сессий: один `pi`-процесс, переключение по требованию~~ (заменено на D12)

> Первая версия держала один процесс pi и `switch_session` при смене сессии. По просьбе
> владельца переделано на мультисессии — см. **D12** (один процесс на сессию). Текст ниже
> оставлен как история решения.

**Решение.** Бот держит **одну** активную сессию (один `RpcClient`). Входящее сообщение из чата:
если у чата есть сохранённый `sessionPath` и он не равен активному — сначала `switch_session`, потом
`prompt`. `agent_settled` → ответ → следующий из очереди. Одновременно живёт не более одного
прогона; входящие во время работы копятся в очереди (как в pi-telegram) и уходят по одному.
`stop` → `abort()`; очередь при этом не теряется, а склеивается в следующий промпт.

**Почему не N сессий параллельно:** каждый `switch_session` пересоздаёт сервисы под свой cwd;
несколько активных сессий = N процессов `pi`, N наборов расширений/MCP и N файлов состояния.
Это кратный рост сложности, которого задача не требует. Ограничение фиксируем в README:
активная сессия одна, переключение мгновенное и идемпотентное.

**FR5 — состояние** (`PI_TG_STATE_DIR/state.json`, атомарная запись temp+rename):
```json
{ "version": 1, "lastUpdateId": 12345,
  "allowedUserId": 42,
  "chats": { "<chatId>": { "sessionPath": "...jsonl", "sessionId": "...", "name": "..." } } }
```
Ключ — `chatId` (топик-формат `chatId:threadId` бесплатно, если понадобится). При старте бот
ничего не переключает, а восстанавливает выбор **при первом сообщении** — так рестарт не зависит
от того, жива ли сессия. Идемпотентность: повторный `/open` той же сессии — no-op.

## D5. Команды бота и маппинг «команда pi → действие» (FR3)

Встроенные команды pi (недоступные через RPC, см. `get_commands`-note) реализуем сами:

| pi | Бот | RPC/SDK |
|---|---|---|
| `pi --resume`, `pi list` | `/sessions` (инлайн-выбор) | `SessionManager.listAll()` |
| `pi --continue` | `/continue` | последняя сессия текущего cwd → `switch_session` |
| `pi --session <path\|id>` | `/open <id\|номер>` | `switch_session` |
| `--name` / `/name` | `/name <текст>` | `set_session_name` |
| `/new`, `pi --no-session` | `/new` | `new_session` |
| `pi --model`, `/model` | `/model <provider/id>` | `set_model` |
| `/thinking`, `--thinking` | `/thinking <уровень>` | `set_thinking_level` |
| `/session`, `pi status` | `/status` | `get_state` + `get_session_stats` |
| `/compact` | `/compact [инструкции]` | `compact` |
| `/stop` (нет в pi, нужен FR4) | `/stop` | `abort` |
| `/help` | `/help` | — |
| `/имя аргументы` из `get_commands` (расширения, шаблоны, `/skill:...`) | как есть | `prompt("/имя аргументы")` |

Свободный текст → `prompt`. Неизвестная `/команда` → человеческая ошибка + подсказка ближайших из
`get_commands`. Не поддержано (и не будет без отдельной просьбы): `/tree`, `/settings`, `/login`,
`/logout`, `/share`, `/bug`, `/trust`, `/reload`, `/scoped-models`, `/import`, `/copy`,
подкоманды `pi install/remove/update/config/auth/mcp`, флаги старта процесса
(`--api-key`, `--system-prompt`, `--append-system-prompt`, `--tools`, …).

| Случай | Ответ в чат |

### Что поменялось по сравнению с первоначальным планом

1. **Путь к CLI.** У `RpcClient` путь по умолчанию (`dist/cli.js`) относительный к cwd процесса,
   поэтому демон из чужого каталога не стартовал бы. Путь резолвится через `import.meta.resolve`
   (`require.resolve` не работает: в `exports` пакета нет условия `require`). Тест — `test/pi.test.js`.
2. **Пустая сессия.** Файл сессии появляется только с первым сообщением, поэтому в состояние
   пишутся только существующие файлы: иначе восстановление после рестарта ломалось бы на
   `switch_session` по несуществующему пути (тест «FR5: сессия без файла на диске…»).
3. **Диалоги расширений.** В RPC-режиме `ctx.hasUI === true` и диалог блокирует ход, поэтому
   реализовано минимально безопасное поведение: штатный ответ `cancelled` + сообщение в чат
   (тест «диалог расширения не вешает ход»). Полные inline-клавиатуры — отдельная задача, FR не требует.
4. **Long polling свой, а не `bot.start()`** — чтобы сохранять `lastUpdateId` в состоянии и не
   переспрашивать апдейты после рестарта (NFR «операции идемпотентны»).
5. **`/export`, `/fork`, `/clone`** сначала были добавлены, но владелец сказал «не нужны» —
   удалены вместе с методами обёртки (лишнего в мосте нет).

### Открытые вопросы — решения по умолчанию (отменяемы)

1. **Расположение**: `self/pi-telegram-bridge`.
2. **Rich Messages** (Bot API 10.1+) не используем: остаёмся на `sendMessageDraft` + конвертер
   GFM→HTML (D3). Вернуться к вопросу, если захочется нативного markdown в стриме.
3. **Выбор сессии** (ответ владельца): кнопками, подпись кнопки — превью сессии (первые слова,
   как в пикере `/resume` у pi). Реализовано в D13, текст `/open <номер|id|имя>` оставлен для
   сессий вне первой страницы.
4. **Мультисессии нужны** (ответ владельца) → D12 вместо D4.
5. **Project trust**: бот сам ничего не решает, только советует `PI_TG_PI_ARGS=--approve`.
6. **Обёртка pi-package** (D9) — сделана, `/telegram-bridge start|stop|status`.

## D12. Мультисессии: один процесс pi на сессию (заменяет D4)

**Решение.** `src/session-pool.js` держит по процессу `pi --mode rpc` на каждую используемую
сессию, ключ — путь сессии. Процесс рождается сразу привязанным к ней:
`pi --mode rpc --session <path>` в рабочем каталоге этой сессии (проверено: `get_state` отдаёт
тот же `sessionId`, см. RESEARCH §8.4). Записи создаются лениво, гасятся по бездействию
(`PI_TG_IDLE_MS`, 30 мин) и вытесняются сверх `PI_TG_MAX_IDLE_SESSIONS` (сверх используемого).

**Почему так, а не `switch_session`.** У сессий разные рабочие каталоги, и `switch_session`
пересоздаёт под каждый все сервисы — переключать туда-сюда значит платить за это на каждом
сообщении и терять параллельность. Отдельный процесс на сессию даёт то, что просил владелец:
разные чаты работают **одновременно**, у каждого своя очередь, прогон и живое сообщение.

**Как устроено.** Очередь и состояние хода переехали из моста в запись пула, поэтому событие
`message_update` обрабатывается в контексте своего процесса (`dispatchPiEvent(entry, event)`).
Чат без сохранённой сессии получает «несвязанный» процесс (ключ `unbound:<chatKey>`); после
первого сообщения pi создаёт файл сессии, запись переезжает под ключ пути (`rekey`), а чат
запоминает путь. Если эта же сессия уже открыта другим чатом, лишний процесс гасится и два чата
живут в одном (защита от параллельной записи в один `.jsonl`).

**Цена.** N процессов pi = N наборов расширений/MCP в памяти (потолок задаёт
`PI_TG_MAX_IDLE_SESSIONS` + idle-таймер). Первое сообщение в «остывшую» сессию ждёт подъём
процесса (секунда-две). Тему форума и чат считаем разными ключами (`chatId:threadId`), т.е.
каждая тема — своя сессия.

**Проверка.** `test/session-pool.test.js` (переиспользование, rekey, слияние, гашение по idle,
LRU-вытеснение, ошибка старта, `stopAll`) и в `test/bridge.test.js` — «мультисессии: два чата
работают каждый в своей сессии», «второй чат в ту же сессию переиспользует процесс».

## D13. Выбор сессии кнопками с превью

**Решение.** `/sessions` печатает список (номер, превью, id, cwd, время) и прикладывает

## Раунд 2: правки по фидбеку владельца (D15–D17)

### D15. Rich Messages вместо самодельного HTML + кнопка «стоп» в клиенте

**Было.** Весь ответ мост сам превращал GFM→HTML (`markdown.js`) и слал с `parse_mode: HTML`.

**Причина правки (фидбек).** Владелец: «делай так, как красивее и функциональнее». Плюс живой
баг: `/start` показал `<b>pi-telegram-bridge</b>` текстом — в справке была строка
`/thinking <off|minimal|…>`, Telegram принял `<off|…>` за тег, отверг разметку целиком, и мост
отправил текст без `parse_mode` (фолбэк). То есть самодельный HTML ещё и хрупкий.

**Решение.** Основной путь — Rich Messages (Bot API 10.1+):
`sendRichMessageDraft(chat_id, draft_id, rich_message: {markdown}, can_stop)` для стрима и
`sendRichMessage(chat_id, {markdown})` для финального сообщения (docs: core.telegram.org
#sendrichmessagedraft / #inputrichmessage — «Exactly one of the fields html, markdown, or blocks
must be used»). Markdown уходит **как есть**, без экранирования и конвертера: `<не тег>` и
`snake_case` больше не ломают разметку. `can_stop: true` даёт нативную кнопку остановки; нажатие
приходит апдейтом `stopped_message_generation` (`{chat, message_thread_id?, draft_id}`), мост по
нему делает `abort()` — это и есть FR4 «stop», но кнопкой в клиенте, а не текстом.

**Фолбэк.** `PI_TG_RICH=auto` (по умолчанию): сбой rich переводит сообщение на классический
путь (черновик → `editMessageText` → `sendMessage` с HTML). Навсегда rich больше не выключается —
см. D31.
`PI_TG_RICH=off` — сразу классика. Плюс мелкая страховка: если Telegram отверг нашу HTML-разметку,
повтор идёт уже **без тегов** (`htmlToPlain`), а не сырым HTML — именно это и выдало баг со справкой.

**Проверка.** `test/live.test.js` (rich-стрим, `can_stop`, многочастность, фолбэк rich→классика,
`rich=off`), `test/bridge.test.js` («FR4: если rich-методы недоступны…», «кнопка "стоп" в клиенте
Telegram прерывает прогон»), `test/commands.test.js` — регрессия «в справке нет сырых `<`» и
`/open &lt;номер|id|имя&gt;`. Вживую: пробное rich-сообщение отправлено в чат владельца, чтобы
увидеть рендер в клиенте.

### D16. Индикаторы в нижней панели pi (📡 у моста, 👾 у agent-skills)

**Фидбек.** «В самом pi с компьютера я не понимаю, включен ли телеграмм мост. Добавь смайлик
спутниковой тарелки, когда мост включен, а когда выключен — убирай. И в agent-skills тоже:
не нужно текстом, пусть просто смайлик.»

**Решение.** Обёртка (`extensions/pi-telegram-bridge.ts`) на `session_start` запускает раз в 5 с
проверку pid-файла и держит `ui.setStatus('2-telegram-bridge', '📡')`, пока процесс жив, и
`undefined`, когда нет (плюс мгновенное обновление после `start`/`stop`). Значение кэшируется,
чтобы не слать `setStatus` без изменений. В пакете `pi-agent-skills` строка статуса сокращена до
`👾` (файл вне этого репозитория: `~/.pi/agent/packages/pi-agent-skills/extension.js`; его
собственный тест `test-extension.mjs` поправлен и проходит).

**Порядок иконок.** Фидбек: «сначала agent skills, потом телеграм, потом ponytail, потом остальное».
`footer.js` рисует статусы в порядке ключей (`localeCompare`), отдельного API порядка у pi нет
(версия 1.1.0), поэтому позиция = имя ключа: свои ключи получили цифровой префикс-ранг
(`1-agent-skills`, `2-telegram-bridge`). Цена: чужие ключи всё равно сортируются по алфавиту —
статус `caffeinate` (активен только во время keep-awake) и `goal` (есть другие открытые цели)
встают между 📡 и 🐴, пока они показаны; чтобы сдвинуть и их, пришлось бы патчить сторонние

(`pi install ./path`).

**Проверка.** `test/extension.test.js`: «📡 появляется, когда демон жив, и убирается, когда
умирает», «индикатор не мигает»; `node test-extension.mjs` в пакете agent-skills.

### D17. `/sessions` без простыни текста + `PI_TG_THREADS`

**Фидбек.** «Помимо кнопок он ещё и сообщением написал все сессии, это не нужно: условно текст
"Список сессий:" и дальше кнопки.»

**Решение.** Сообщение сокращено до заголовка `<b>Список сессий</b> (N):` и, если у чата есть
активная сессия, одной строки о ней (`▸ сейчас: имя · id · время`). Данные FR1 (id, cwd, время)
остаются доступны: превью — в кнопках, детали активной сессии — строкой, `/status` — по текущей.
Новый `PI_TG_THREADS=separate|shared` (по умолчанию separate) отвечает на вопрос владельца
«не понял» про темы форума: каждая тема = своя сессия; `shared` ведёт все темы в одну сессию чата.

**Проверка.** `test/bridge.test.js`: «FR1: /sessions — короткий заголовок и кнопки с превью»

## Раунд 3: дебаг «бот встал» (D18)

**Симптом.** Владелец: «написал боту сообщение, он начал обрабатывать, но дальше просто встал».

**Что было на самом деле** (по логу и файлу сессии):
1. Чат был привязан к сессии `01a12aa6` — это сессия, открытая в терминале. Бот поднял на ней
   свой `pi --mode rpc` и начал ход: получил сообщение владельца, пошёл читать документацию
   Telegram, правил `src/`, гонял тесты (110 → 117) — то есть работал, а не висел.
2. В 17:02:31 в лог записалось `SIGTERM: останавливаюсь`, и демон вместе с процессом pi умер.
   Последняя запись в сессии — `toolCall:bash` ровно в 17:02:31, результата у него уже нет.
   То есть ход был прерван **извне**: сигнал пришёл от того же bash-tool'а (агент мог перезапускать
   мост по pid-файлу) либо от `/telegram-bridge stop` в pi. Ни одна ветка кода моста тут не
   «зависла» — просто исчез процесс, о чём чат не мог узнать.

**Почему чат не узнал.** В мосте не было подписки на выход дочернего процесса: если pi умирал
посреди хода, `busy` оставался `true`, живое сообщение не финализировалось, а следующие сообщения
уходили в очередь навсегда. Это тот самый пробел, который я раньше отметил как
«не воспроизводилось вживую» — воспроизвелось.

**Исправлено (D18).**
- `src/pi.js`: на child процесса вешается `exit` → синтетическое событие `pi_exit`
  (`{code, signal, stderr}`) уходит подписчикам (RpcClient сам такого события не отдаёт —
  `shortcut:` в коде).
- `src/bridge.js`: `onPiExit` выгребает очередь, гасит запись пула (мёртвый процесс не пытаемся
  использовать), закрывает ход ошибкой «процесс pi остановился (код …): <последняя строка stderr>»
  в том же живом сообщении и предупреждает каждый чат из очереди «повторите сообщение».
  Следующее сообщение поднимает сессию заново.
- Ходы теперь логируются на уровне `info`: `ход: <сессия>, N симв. промпта` и
  `ход завершён за X с · текста N симв.` — в следующий раз из лога сразу видно, шёл ход или нет.

**Проверка.** `test/bridge.test.js` → «падение процесса pi закрывает ход ошибкой и снимает
занятость» (ошибка в чат, предупреждение очереди, запись пула погашена, следующий промпт уходит в
новый процесс).

**Вывод для эксплуатации.** Telegram-агент имеет полный доступ к машине (включая bash), поэтому
он в принципе может остановить свой же мост. И не стоит вести один чат и терминал в одну сессию
(`.jsonl` пишут два процесса). Рекомендация владельцу: держать под бота отдельную сессию
(`/new`) или другой каталог.

## D20. Статусы скиллов, контекст и баланс в `/status` + тишина caffeinate

**Фидбек.** «Почему в Telegram всё время висит ℹ️ Keeping computer awake (display-awake)?
Не присылай его, лучше в виде таблицы показывай статусы трёх скиллов 👾📡🐴 (наличие статуса =
включено, текст не нужен), а также контекстное окно и остаток денег на счету api».

**Caffeinate — не наш код.** Сообщение шлёт `pi-caffeinate` через `notify` при каждом включении
ингибитора, а мост по устройству пересылает `notify` в чат. У самого расширения есть штатная
настройка `quiet` (`~/.pi/agent/pi-caffeinate.json`), она глушит рутинные уведомления и убирает
статус `caffeinate`. Правим настройку, а не мост: фильтровать чужие уведомления по тексту —
хрупко, а `quiet` ещё и чинит это в терминале.

**Ponytail — так же.** «Ponytail loaded: full» летит на каждый `session_start` дочернего pi
(а дочерний pi мост поднимает на каждую сессию), поэтому после перезапуска демона это сообщение
снова приходило в чат. Гасится его же настройкой `quietStartup` в `~/.config/ponytail/config.json`
(путь — `getConfigPath` в `hooks/ponytail-config.js`, есть ещё env `PONYTAIL_QUIET_STARTUP`);
индикатор 🐴 не трогаем (`hideStatus` — отдельный ключ). Проверено зондом на настоящем
`pi --mode rpc`: за старт сессии теперь ни одного `notify`.

**Таблица.** Источник данных — уже идущий поток: в RPC-режиме `ctx.ui.setStatus()` расширений
дочернего pi приходит мосту как `extension_ui_request` method=`setStatus`
(`docs/rpc-extension-ui.md`; раньше мост его молча игнорировал). Теперь он складывает пары
ключ→текст в запись пула (`src/session-pool.js`, `entry.statuses`), а `/status` строит из них
строку «Скиллы» по трём ключам (`1-agent-skills`, `2-telegram-bridge`, `ponytail`) и строку
«Баланс API» из статуса `usage` (pi-usage держит там ответ `api.deepseek.com/user/balance`).
Альтернативы: свой запрос баланса (лишний HTTP-клиент и второй источник секрета — ключ из
`~/.pi/agent/auth.json`, чего проект избегает) и чтение статусов через подмену footer —
не нужно. ANSI-цвета чужих статусов вырезаются в `stripAnsi`, текст экранируется.
Цифры баланса, контекста — то же, что видно в нижней панели терминала; наличие значка = статус
выставлен, сняли статус — значок исчез.

**Проверка.** `npm test` — 121 тест: `test/status.test.js` (значки, прочерки, ANSI, экранирование),`test/bridge.test.js` («статусы расширений из дочернего pi попадают в /status значками и балансом»).
Вживую (зонд на настоящем `pi --mode rpc`, без вызова модели): приходит
`1-agent-skills=👾`, `2-telegram-bridge=📡`, `ponytail=…🐴…`, `usage=deepseek USD 8.33`, а `/status`
отдаёт таблицу со строкой «Скиллы | 👾 📡 🐴»; после `quiet: true` — ни одного сообщения caffeinate.
Осталось незаглушённым `notify` самого ponytail («Ponytail loaded: full», один раз на старт
сессии) — владелец про него не говорил, при желании глушится его же `quietStartup`.

## D21. Живая строка хода: мысль модели вместо «думаю…»

**Фидбек.** «Сообщение „думаю“, которое всё время меняется, лучше переделать: там либо думаю,
либо bash. Можно что-то смешное про мыслительный процесс, либо реально показывать это мышление —
не целиком, пару строк, постоянно меняющихся».

**Решение.** В живой строке теперь три уровня: заметка хода (сжатие/повтор/таймаут) → **хвост
настоящей мысли** (`thinking_delta` из RPC: последние 180 символов одной строкой, с `💭`,
markdown-символы внутри вырезаются иначе курсив вокруг статуса ломается) → `⚙ инструмент` →
фраза из списка, меняющаяся каждые 5 с по времени от начала хода (не по часам — так тесты
предсказуемы). Раз в 4 с ход будит живое сообщение тикером, чтобы фраза успевала смениться;
если текст не изменился, `live.js` ничего не отправляет. Мысль идёт только в живой строке:
в финальном ответе её нет. Провайдер, который рассуждений не отдаёт, просто никогда не попадёт
во вторую ветку — проверено на `deepseek-flash` с тривиальным промптом (0 thinking-дельт)
и на задаче с арифметикой (19 дельт).

**Про анимацию печати.** Владелец отдельно похвалил медленный набор текста в драфте и просил
использовать его «где уместно». Он уже используется во всех ответах модели (стрим дельт);
для ответов команд синтетическая печать — это искуственная задержка в 2–3 с и риск дублей
(черновик финализируется отдельным сообщением), поэтому её не добавляли. Если владелец захочет —
включается в `sendMarkdown` теми же `live.update()`.

**Проверка.** `npm test` — 122 теста, новый — «FR4: в живом сообщении видно, о чём думает модель»
(хвост, вырезанный markdown, приоритет над именем инструмента, обрезка).

**Заменено D34:** текст мыслей в чат больше не идёт — только смешные фразы по таймеру.

## D22. Узкие ячейки в `/status`: пути и имя сессии — вне таблицы

**Фидбек.** «Тут правый столбец очень широкий, хотя столько места не нужно, а левый короткий

## D23. Лог демона при старте из pi

**Найдено рядом.** Обёртка поднимает демон с `stdio: "ignore"` — после `/telegram-bridge start`
не оставалось ни лога, ни строчки в `bridge.log`, по которой можно понять, жив ли мост и что он
делает (именно на это я наткнулся после первого перезапуска).

**Решение.** Обёртка открывает `~/.pi/agent/pi-telegram-bridge/bridge.log` (`а`) и отдаёт этот
дескриптор ребёнку в `stdio: ["ignore", log, log]`, в родителе дескриптор закрывается сразу.
Файл — рядом с проверенным pid-файлом, путь видно в ответе команды. Альтернатива — писать в
`bridge.log` репозитория — была бы ложью: демон можно поднять из любого каталога (или из другого
проекта), а состояние уже живёт в `~/.pi/agent/pi-telegram-bridge`.

**Проверка.** `npm test` — 123 теста (путь старта в тестах не гоняется: настоящий `start` поднял бы
второй бот и дал `409`). Механику проверил отдельным запуском: тот же `stdio` с дескриптором файла
— вывод ребёнка оказался в логе. Живьём: после `/telegram-bridge start` (нужен перезапуск pi или
`/reload`, чтобы pi перечитал расширение) в логе появляются строки старта моста.

## D24. Заголовки ответов без засечек

**Фидбек.** «Не нравится, что заголовки твоих ответов шрифтом с serifs, а базовый текст нет».
В rich-режиме markdown уходит Telegram как есть, и `# Заголовок` он рисует крупным шрифтом
с засечками. В классическом пути такого не было: `toTelegramHtml` давно делает из заголовка `<b>`.

**Решение.** Перед отправкой в rich `headingsToBold` (`src/markdown.js`) превращает `#{1,6} …`
в `**…**` — и в черновике, и в финальном сообщении. Код-блоки не трогаем: там решётка — это код.
Альтернатива — просить модель не писать заголовки — не наша зона и зависит от промпта.

**Проверка.** `test/markdown.test.js` («заголовки становятся жирным текстом»),
`test/live.test.js` («rich: заголовки уходят жирным текстом, код-блок остаётся как есть»).

## D25. Укороченный статус в живой строке

**Фидбек.** «Хочу, чтобы при генерации ответа висел укороченный status и обновлялся в реальном
времени в следующем порядке: скиллы, токены, контекст, стоимость, баланс».

**Решение.** Живая строка стала двухслойной: сверху «что происходит» (заметка хода → хвост мысли
💭 → запущенный инструмент), снизу — та же пятёрка, что в `/status`, но без обвязки:
`👾 📡 🐴 · ↑10k ↓2.0k · 6% из 200k · $0.042 · USD 8.36` (`formatLiveStatus` в `src/status.js`).
Цифры берём из `get_session_stats` (токены, контекст, стоимость) — запрос на старте хода и в тике
раз в 4 с; баланс — из статуса `usage` (pi-usage), скиллы — из статусов дочернего pi.
Ничего не выдумываем и не ходим в чужие API: всё течёт тем же потоком, что и в терминале.
Смешная фраза осталась фолбэком: она появляется, только пока о ходе ещё ничего не известно.
Курсив навешивается на каждую строку отдельно (`live.js`), иначе `_`
развалился бы на две строки.

**Проверка.** `npm test` — 127 тестов: `test/status.test.js` («живая строка: … в этом порядке»,
«живая строка растёт»), `test/bridge.test.js` («FR4: в живом сообщении видно, о чём думает модель» —
там же проверяется вторая строка с цифрами).

## D26. Зависший pi не блокирует чат: abort с таймаутом и два watchdog-таймера

**Проблема.** Если `abort` не получил ответ (зависший stdin/процесс), `doStop` оставлял запись
`busy` навсегда: новые сообщения копились в очереди, а процесс не гасился. Тишина модели тоже
никогда не заканчивала ход.

**Решение.** В `bridge.js` вокруг `abort` — свой таймаут 10 с. На неудаче/таймауте: `failTurn`
(живое сообщение получает ошибку), `pool.dispose(entry)` (запись уходит, процесс убивается),
очередь предупреждается. Следующее сообщение поднимает свежий процесс. То же — для нативной
кнопки «стоп» в клиенте Telegram.

Два таймера хода (`src/watchdog.js`):
- **тишина** `PI_TG_TIMEOUT_MS` (15 мин) — перезапускается на каждом событии `dispatchPiEvent`,
  пишет заметку в живой строке «Нет событий N — pi молчит. /stop прерывает»;
- **абсолютный потолок** `PI_TG_TURN_MAX_MS` (20 мин) — не сбрасывается событиями, делает
  `failTurn` + `abort` + `dispose` и текст в чат.

**Цена.** Два таймера на ход (unref, гаснут в finish/fail/stop). Таймаут abort 10 с — задержка
ответа на `/stop` только в уже сломанном случае.

**Проверка.** `test/watchdog.test.js` на фейковых таймерах (сброс событиями, несбрасываемый
потолок), `test/bridge.test.js` — «P0: если abort не отвечает…» и «watchdog: абсолютный потолок…».

## D27. Потолок процессов, pid-lock и память на Raspberry Pi

**Решение.** `PI_TG_MAX_PROCESSES` (по умолчанию 4, на Pi — 3) проверяется в
`session-pool.start()` до `pi.start()`; сверх потолка — ошибка в чат «занято N сессий, попробуй
позже или /stop», процесс не спавнится. `src/pid-lock.js` берёт `bridge.pid` рядом с `state.json`
через `openSync('wx')`: живой чужой pid — выход с текстом, устаревший — замена, свой pid — это
запись обёртки-расширения (она пишет файл после spawn), удаление на shutdown. `PI_TG_CWD` из
обёртки больше не перезаписывается, если уже задан. `client.stderr` SDK обрезается до 64 КБ
(`shortcut:` в `src/pi.js`, версия SDK 1.1.0). `/stop` ищет запись через `pool.find` и не поднимает
процесс, если прерывать нечего.

**Почему.** Второй демон на том же токене даёт `409`; без потолка 4 ГБ Pi уходят в swap. Точный
расчёт памяти — в README, раздел «Запуск на Raspberry Pi».

**Проверка.** `test/pid-lock.test.js` (живой/устаревший/свой pid, release), `test/bridge.test.js`
(«потолок процессов…», «/stop без записи…»).

## D28. Голос через OpenRouter STT

**Решение.** `bot.on('message:voice')` и `message:audio`: файл скачивается через Bot API
(`getFile` + `https://api.telegram.org/file/...`), уходит POST в `${STT_BASE_URL}/audio/transcriptions`
с JSON `{input_audio:{data:<base64>, format}, language, model}` и `Authorization: Bearer
OPENROUTER_API_KEY`. По умолчанию `openai/whisper-large-v3`, язык `ru`. Лимиты 10 минут / 20 МБ
проверяются до скачивания (и после — по фактическому размеру), отказ — текстом. Транскрипт уходит
обычным путём в сессию с префиксом `[голос 3:42] `. 20 МБ — не наше ограничение: `getFile` больше
не отдаёт. Таймаута на STT нет: whisper-large тратит на 10 минут звука 20–40 с, обрыв ждал бы впустую;
таймаут остался только на зависание скачивания (15 мин).

**Почему fetch, а не SDK.** Node 22 имеет встроенный fetch; новая зависимость ради одного POST не
нужна. Ключ только в заголовке, в ошибки/логи не попадает.

**Ошибки.** Любая ошибка скачивания/STT/пустого ответа — сообщение в чат; без
`OPENROUTER_API_KEY` — «Голос не настроен». Фото/document обрабатываются с D33; sticker/video
получают короткий отказ без запуска pi.

**Проверка.** `test/voice.test.js` (лимиты, формат, запрос, разбор ответа, ошибки через мок fetch),
`test/bridge.test.js` (голос → префикс в prompt, лимиты без spawn, ошибка STT, не-текстовые).

## D29. Группы: только адресная реакция

**Решение.** В личке бот отвечает на всё. В группе/супергруппе — только если в тексте/подписи есть
`@username` бота или сообщение является ответом на сообщение бота; команды (`/...`) разрешены
всегда. `PI_TG_REQUIRE_MENTION=false` снимает фильтр для групп. Тег бота вырезается из промпта,
чтобы модель не видела служебное упоминание. `/start` в группе не спаривает: спаривание только в
личке (иначе первый `/start` привязал бы бота к случайному участнику). Кнопки `/sessions`
работают и в группе: нажатие — адресованное действие, доступ проверяется по `allowedUserId`.

**Цена.** В группе с выключенным privacy mode бот получает всю переписку, но молчит без адреса;
это экономит токены и не даёт боту влезать в разговор.

**Проверка.** `test/bridge.test.js` — «адресация: в личке…», «@бот и reply…», «команды в группе…».

## D30. Длинные ответы: таблицы режутся по строкам, шапка повторяется

**Причина.** `chunkText` резал markdown и HTML по символам: длинная таблица теряла шапку, а
HTML-таблица обрывалась посреди тега. Telegram отвергал разметку или показывал её простым
текстом — это и видел владелец.

**Решение.** В `src/chunk.js` три режима: `chunkText` (простой текст, как раньше), `chunkMarkdown`
(таблицы — по строкам; в каждой следующей части повторяются шапка и разделитель; списки и
абзацы режутся по строкам) и `chunkHtml` (наши HTML-сообщения: таблица разбирается на `<tr>`,
повторяется `<table>` + первая строка-шапка; длинные строки режутся без разрыва тега, открытые
inline-теги закрываются и открываются снова). `live.js` режет markdown до конвертации, а HTML —
после; `bridge.sendMarkdown` режет HTML для своих ответов. Черновик живой строки режется по
границе строки/тега, а не по символам.

**Цена.** Больше кода в `chunk.js`; таблица может уехать в отдельное сообщение, даже если часть
текста до неё влезла бы. Строка таблицы длиннее 4096 символов по-прежнему режется жёстко —
это крайний случай, таблицу в ней сохранить нельзя.

**Проверка.** `test/chunk.test.js` — 60-строчная markdown-таблица (шапка в каждой части, строки
не потерялись), 60-строчная HTML-таблица (нет обрыва посреди тега, шапка повторяется), длинный
inline-тег; `test/live.test.js` — таблица из 60 строк уходит несколькими rich-сообщениями.

## D31. Rich-сообщения: после сбоя повтор через N сообщений

**Причина.** `richSupport`/`richForOwnMessages` выключались навсегда после первой же ошибки
метода. Одна временная ошибка — и до перезапуска бота все таблицы шли классическим путём, где
Telegram не умеет `<table>`; таблицы выглядели простым текстом.

**Решение.** `src/rich.js`: `createRichGate()` с окном `RICH_RETRY_MESSAGES = 10`. Сбой пишет в
лог `rich-сообщения не сработали (…); 10 сообщений — классический путь, потом попробую снова` и
включает окно; каждое следующее сообщение уменьшает счётчик, после окна rich пробуется снова.
Один gate на мост, его делят живое сообщение и ответы команд; `resetRichSupport()` остался для
тестов live.

**Цена.** Если rich недоступен на сервере постоянно, раз в 10 сообщений будет одна лишняя
неудачная попытка (и запись в лог). Это дешевле, чем навсегда потерять таблицы.

**Проверка.** `test/bridge.test.js` — «ответы команд… повтор через N сообщений»;
`test/live.test.js` — «после N сообщений… попытка rich повторяется».

## D32. Файлы от агента: маркер `[file:…]` и sendDocument

**Решение.** `src/files.js` вынимает из ответа строки `[file:/abs/path]`. Путь проверяется после
`realpath`: он обязан лежать внутри `${PI_TG_DATA_DIR}/outbox` или `/inbox` (по умолчанию
`/srv/assistant/data`), быть файлом и весить не больше 50 МБ. Валидный файл уходит
`sendDocument`; если весь видимый текст — короткий текст до маркера (≤1024), он становится
подписью, иначе текст уходит обычным сообщением, а файл — без подписи. Ошибка проверки или
отправки — текст в чат. Маркер пользователю не показывается.

**Почему `realpath`.** Симлинк из inbox на `/etc/passwd` иначе обошёл бы проверку префикса.
Проверяются и исходный путь, и реальный.

**Проверка.** `test/files.test.js` (маркер, outbox/inbox, симлинк наружу, 50 МБ, имена),
`test/bridge.test.js` — «файл из ответа…» (sendDocument с подписью, путь вне каталогов — отказ).

## D33. Входящие фото и документы → inbox

**Решение.** `message:photo`: выбирается самый крупный размер (по `file_size`, иначе по площади),
файл скачивается в `${PI_TG_DATA_DIR}/inbox/photo-<ts>.jpg`. Если у `RpcClient` есть
`prompt(message, images)`, фото уходит как `ImageContent` (base64 + `image/jpeg`), подпись — текст
промпта; иначе — `[фото: <путь>] <caption>` и просьба разобрать файл инструментами.
`message:document`: pdf/docx/xlsx/txt/csv/json/zip (по расширению или MIME) до 20 МБ,
`<orig>-<ts>.<ext>` (имя очищается), затем `[документ: <путь>] <caption>` и та же просьба.
Любая ошибка скачивания/размера — сообщение в чат; тишины нет.

**Почему путь, а не файл в RPC.** RPC умеет только изображения; PDF/DOCX агент читает своими
инструментами (`read`/`bash`), поэтому ему нужен путь на диске.

**Проверка.** `test/files.test.js` (расширения, MIME, размер, безопасное имя), `test/bridge.test.js`
(фото картинкой и текстом, документ, чужой формат/размер, ошибка скачивания).

## D34. Мысли модели не в чат: смешные фразы по таймеру

**Фидбек.** Хвост рассуждений (`💭`) в живом сообщении — это внутренний текст модели; владелец
попросил заменить его короткими смешными фразами о процессе.

**Решение.** `dispatchPiEvent` больше не хранит `thinking_delta`/`thinking_end`; события лишь
сбрасывают заметку и обновляют живую строку. `statusLine` показывает: заметку хода → `⚙`
запущенный инструмент → фразу из списка. Фраза выбирается по времени от начала хода,
`PHRASE_PERIOD_MS = 4000`; тикер живой строки тоже раз в 4 с, поэтому фраза успевает смениться.
Список — про работу с деньгами/сметами («пересчитываю смету в уме…», «сверяюсь с прайсом…»,
«прикидываю, где сэкономить…» и т.д.).

**Проверка.** `test/bridge.test.js` — «мысли модели не попадают в чат…»: текст `thinking_delta`
и `thinking_end` не появляется в драфте, фраза меняется при сдвиге времени, `⚙ bash` её вытесняет.

## D35. Меню и навигация по проектам без Mini App

**Фидбек.** Mini App и HTTPS-туннель отключены («пока что отключи»), но данные остались
на Pi: локальный API `http://127.0.0.1:8088` (`/api/projects`, `/api/estimate?id=`, `/api/pdf?id=`)
с заголовком `x-service-token`. Нужна навигация кнопками прямо в Telegram.

**Решение.** `/start`, `/menu` и слово «меню» присылают «Чем помочь?» и клавиатуру
`📁 Проекты` / `🆕 Новая смета` / `🧾 Клиенты` / `❓ Помощь`. Ветка проектов не поднимает
процесс pi: `src/assistant-api.js` ходит в локальный API (таймаут 5 с, база `MINIAPP_API_URL`,
токен `MINIAPP_SERVICE_TOKEN`, кеш ответов 30 с), `src/assistant.js` строит тексты и клавиатуры
чистыми функциями. Объекты листаются по 8 на страницу, карточка показывает заказчика и последнюю
версию, версия — строки, итог, скидку 5 % за наличные и сумму к оплате; PDF уходит `sendDocument`
из буфера. Callback отвечает сразу, долгая загрузка идёт отдельным «⏳ собираю…» с правкой того же
сообщения, ошибка API становится текстом «не смог получить …: причина». Кнопки перехватывают
только свои callback-данные и точное слово «меню»; остальной текст по-прежнему уходит в pi.

**Почему кеш в клиенте.** Навигация — это несколько тапов подряд по одним и тем же данным;
30 с совпадают с уже принятым кешем списка сессий и не дают дёргать SQLite на каждое нажатие.

**Цена.** После правки в базе до 30 с в чате может быть старая карточка — обновится следующим
тапом. `🆕 Новая смета` и `🧾 Клиенты` пока честно отвечают тостом «недоступно»: отдельных
API для них нет, а придумывать запись в базу из моста — не эта задача.

**Проверка.** `test/assistant-api.test.js` (разбор ответов, таймаут/403/404, кеш 30 с),
`test/assistant.test.js` (меню, пагинация, эмодзи, карточка, версии, скидка, экранирование),
`test/bridge.test.js` (меню тремя входами, список/объект/версия/смета, PDF из буфера,
ошибка API текстом, кеш на повторном тапе).

## D36. Потолок стоимости одного прогона — $2

**Решение.** Мост берёт фактический расход из pi (`getSessionStats().cost` — сумма за всю сессию)
и считает стоимость прогона как разницу с расходом до начала хода. Перебор
`PI_TG_TURN_MAX_COST_USD` (по умолчанию 2) останавливает прогон: `abort`, процесс гасится,
в чат уходит «остановил себя: прогон стоил больше $2 (факт $…)», факт пишется в лог (`log.warn`).

**Альтернативы.** (A) Считать по токенам и тарифу модели — своя формула цен, расходится с
реальным счётом; (B) бюджет на сессию, а не на прогон — не отвечает требованию владельца
(«потолок одного вызова»); (C) ограничение на стороне pi — таких настроек у провайдера нет.

**Цена/риск.** Проверка идёт по событиям конца ответа и раз в 4 с, поэтому перебор внутри одного
ответа модели виден уже после его оплаты: лимит останавливает прогон, но не отменяет последний
вызов. При недоступной статистике (`getSessionStats` упал) лимит молчит — как и раньше молчал
watchdog при отсутствии событий.

**Проверка.** `test/bridge.test.js` («лимит стоимости прогона»: перебор и в пределах лимита),
`test/config.test.js` (значение и мусор в env), живой прогон `scripts/live-cost-limit.js`
(настоящий pi и настоящий расход, Telegram подменён печатью вызовов).

## D37. PDF одноразовый и настоящий e2e вместо «поддельного Bot API в обработчике»

**Решение.** Документ сметы не хранится: после успешной отправки мост удаляет `*.pdf`, а уборка
(раз в час в мосте и ночной `upkeep` ассистента) добивает те, что не ушли. В `outbox/<id>/`
постоянно лежит только лёгкое — `smeta.csv` и `estimate.json`; PDF из них пересобирается
байт в байт (проверка в `assistant/test/pdf-estimate.test.js`).
Сквозной путь проверяется отдельным набором `npm run e2e`: настоящий процесс `pi` с инструментами
ассистента, настоящий PDF и `sendDocument`; подменены только Bot API (локальный HTTP) и модель.

**Альтернативы.**
| Вариант | Почему отказ |
|---|---|
| Хранить PDF рядом со сметой | 17 МБ мусора на Pi и второй источник правды: документ собирается из состава и сумм |

**Цена/риск.** `npm run e2e` требует каталог ассистента рядом и запускает настоящий pi: ~5 с,

## D38. Одна сессия на чат: `dm:<userId>` / `group:<chatId>`, тема форума её не меняет

**Решение.** Ключ привязки в `state.json` — `dm:<userId>` для лички и `group:<chatId>` для группы;
`threadId` из ключа убран. Файл сессии переиспользуется всегда, пока он есть на диске: привязка
пишется сразу после старта хода (файл уже создан) и обновляется при компакции. Пустой путь больше
не стирает известную привязку (`persistChat` не трогает запись, если файла ещё нет) — это и была
причина «новый файл на каждое сообщение». Новая сессия заводится только если файл пропал, и это
видно в логе (`файл сессии … пропал — завожу новую`) и в `state.json`.

**Альтернативы.** Ключ «чат + тема» (было) — на Raspberry Pi это 53 файла: каждая тема форума и
каждый перезапуск заводили новую сессию, история дробилась. Ключ по `sessionId` — не годится:
после компакции id меняется, а нам нужна та же сессия.

**Цена/риск.** Требование владельца «максимум три сессии» теперь свойство кода, а не привычки.
`PI_TG_THREADS` остался только для ключей интерфейса (меню/списки). Миграция старых файлов —
`scripts/migrate-sessions.js` (выбор самой свежей привязки на чат, остальное в
`~/.pi/agent/sessions-archive/<дата>/`).

**Проверка.** `test/state.test.js` (ключи и миграция старых), `test/bridge.test.js`: «одна сессия
на чат: три сообщения подряд дают один и тот же файл», «три чата — три сессии, тема форума сессию
не меняет», «рестарт моста не заводит новый файл сессии», «файл сессии пропал → новая привязка».

## D39. Полный инструментарий агента на Pi и права на перезапуск служб

**Решение.** В `deploy/assistant-bridge.service` (копии в репозитории ассистента и на Pi)
`PI_TG_PI_ARGS` пуст: агент получает `bash`, `edit`, `write`, `powershell` и MCP, сам правит код,
конфиг и деплоит. Перезапуск и чтение состояния служб контура — без пароля, правило
`deploy/assistant-agent.sudoers` → `/etc/sudoers.d/assistant-agent` (`visudo -cf` перед установкой).
Дисциплина (в `AGENTS.md` моста и `deploy/work/AGENTS.md` ассистента): перед правкой кода —
`git status`/ветка, прод не ломать без `npm test`, после правки — перезапуск служб и сообщение
владельцу; код и конфиг правятся только через git, напрямую — только данные в `/srv/assistant/data`.

**Альтернативы.** Оставить `--exclude-tools` — владелец запретил: «считай, что он абсолютно
самостоятельный». Расширить sudoers до `/bin/systemctl` целиком — лишние права без пользы; список
юнитов фиксирован и проверяется `visudo`.

**Цена/риск.** Прежняя строка `PI_TG_PI_ARGS=--exclude-tools … --no-mcp` из-за пробелов без
кавычек вообще не работала (systemd: `Invalid environment assignment, ignoring`), то есть
ограничения не действовали уже до этой правки — см. `docs/PROJECT-STATE.md` ассистента. Риск
осознан: доступ есть только у двух фаундеров, мост отвечает только им.

**Проверка.** Живой прогон на Pi (`pi -p`): агент выполнил `ls /srv/assistant` и создал
`/tmp/agent-check.txt`; `sudo -n systemctl restart assistant-bridge` без пароля.

**Уточнение владельца (28.10.2026): пароль — не проблема.** На этом Pi у `minibrick` уже есть
`NOPASSWD: ALL` (`/etc/sudoers.d/010_pi-nopasswd`), поэтому узкое правило — про рутину и про случай,
если общее правило снимут. Шире списка юнитов агент идёт по протоколу из `deploy/work/AGENTS.md` §8.0:
одна строка в чат «пришли пароль sudo для <что делаю>», затем `printf '%s\n' "<пароль>" | sudo -S -k
<команда>` на одну команду, пароль не пишется в файлы, историю, логи и код и не повторяется в ответе;
сначала пробуется `sudo -n`, отказ — просьба пароля. Проверено, что неинтерактивный `sudo` не висит:
`sudo -S` с закрытым stdin и с задержкой в 2 с завершается за то же время (`timeout 5` не срабатывает),
у пользователя без правил — сразу `sudo: a password is required`.

## D40. Форматирование: rich-финал не зависит от черновиков, таблица в классике — `<pre>`

**Решение.** Три правки в отправке ответа:
1. `live.js`: отказ черновика (`sendRichMessageDraft`/`sendMessageDraft`, чаще всего
   `TEXTDRAFT_PEER_INVALID` в группах) больше не означает отказа rich-сообщения. Раньше первый же
   отказ черновика вызывал `richGate.fail` и на 10 сообщений отправлял ответы классикой — таблицы
   сметы приходили палками и `| --- |`. Теперь `richFinal` — отдельный флаг, живая строка уходит на
   классику, финал остаётся rich; чат с недоступными черновиками запоминается (без повторных проб).
2. `markdown.js`: GFM-таблица превращается в `<pre>` с шапкой, линейкой и выровненными числами
   (в `parse_mode: HTML` таблиц нет — docs/RESEARCH.md §8.5). Маркеры разметки внутри ячеек
   снимаются, текст экранируется.
3. `chunk.js`: нарезка HTML идёт одним проходом со стеком открытых тегов — каждая часть закрывает
   их и открывает снова, поэтому `<pre>`/`<blockquote>`/`<b>` не рвутся на границе 4096. Часть
   считается влезающей, если влезает и как markdown, и как HTML (`fitsBoth`), поэтому таблица не
   разрезается без шапки. Последний резерв — `markdownToPlain` (простой текст без разметки).

**Альтернативы.** Отправлять таблицу HTML-таблицей — Bot API не знает `<table>` в `parse_mode:
HTML`, сообщение отвергается целиком. Оставить таблицы только в rich — тогда при недоступном rich
ответ теряет смысл; `<pre>` читаем и валиден.

**Цена/риск.** Моноширинная таблица в классике выглядит проще, чем rich-таблица (нет рамок и
переносов), зато числа не разъезжаются и шапка не теряется. Ширина символов считается по
кодовым точкам (`\p{Extended_Pictographic}` = 2) — составные эмодзи (ZWJ) считаются на 1 шире.

**Проверка.** `src/format-check.js` + сквозной сценарий «(е) форматирование» в `npm run e2e`
(таблица, `<>`/`&`, длинная строка, таблица на 60 строк, эмодзи; проверяется текст и `parse_mode`,
которые реально ушли в Bot API), юнит-тесты `markdown`/`chunk`/`live` (включая «нет непарных тегов
после нарезки»). До правки probe давал `| --- |` в чате — после правки проблем нет.
