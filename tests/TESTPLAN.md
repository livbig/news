## 1. Тестовое окружение и мок-стратегия (прогон без токенов)

### 1.1 Telegram Bot API

- **Fake-обновления (CI, без токена):** синтетические объекты `Update`
  (Message, CallbackQuery) подаются в aiogram Dispatcher напрямую
  (`dispatcher.feed_update()`). Сетевой long polling не выполняется.
- **Fake-отправитель:** транспорт Bot API подменён моком
  (`MockTelegramSender`), который: (а) записывает все исходящие сообщения и
  `sendChatAction` в буфер; (б) строго валидирует HTML (`parse_mode=HTML`)
  стандартным парсером — битая разметка = провал теста; (в) по флагу умеет
  отвечать 429 с `retry_after`.
- **Полностью без `TELEGRAM_TOKEN`:** активируется штатный mock-режим
  (решение D20) — сводка выводится в stdout; так гоняется TC-42.
- **Реальный токен:** только ручной smoke-тест после итерации 7, в CI не
  входит.

### 1.2 LLM (Z.ai GLM)

- **Без `LLM_API_KEY`:** штатный mock-генератор `bot/llm.py` —
  детерминированная сводка «заголовок — ссылка» с пометкой (mock). Базовый
  режим всех автоматических кейсов.
- **Проверка ошибок/ретраев:** `llm_base_url` конфигурируется на
  локальный fixture-сервер (§1.4): сценарии «всегда 500», «таймаут»,
  «200 с телом сводки».

### 1.3 Внешние источники

- Все коллекторы (`rss`, `html`, `tgweb`, `reddit`, `twbridge`) гоняются
  против **локального fixture-сервера** (aiohttp, localhost): адреса
  источников и `TWITTER_BRIDGE_URL_TEMPLATE` в тестовом конфиге указывают
  на его маршруты. Реальные внешние URL — только ручной smoke.
- `t.me/s/`-коллектор: маршрут отдаёт копию HTML веб-превью канала;
  негативный маршрут отвечает 403/redirect на логин.
- Reddit-маршрут отдаёт `.json`; деградационный маршрут отвечает 429.

### 1.4 Fixture-файлы (содержимое — данные, не код)

`rss_valid.xml` (3 элемента, свежие даты) · `rss_unchanged.xml` (те же 3
элемента) · `rss_big.xml` (150+ элементов для превышения 4000) ·
`rss_special_chars.xml` (заголовки с `<b>`, `&`, `_`, `[x](y)`, `*`,
обратные кавычки) · `html_list.html` (страница со списком ссылок на
статьи) · `html_garbage.html` (страница без распознаваемой структуры) ·
`tgweb_open.html`, `tgweb_closed` (403) · `reddit_new.json`,
`reddit_429` (маршрут) · `bridge_feed.xml`, `bridge_503` (маршрут) ·
`llm_500` (маршрут).

### 1.5 Время и БД

- **FakeClock:** инжект `now()` в планировщик/дайджест; слоты и catch-up
  проверяются «перемоткой» времени без реального ожидания; порог FSM-таймаута
  в тестах снижается до секунд.
- **БД:** временный файл или `:memory:` SQLite со схемой, создаваемой
  `bot/db.py`; состояние проверяется прямыми SQL-запросами к
  `users/sources/items/digests` (план §1.2).

## 2. Тест-кейсы

### 2.1 Unit

ID: TC-01 | FR: FR-02 | Приоритет: P0 | Тип: unit
Что проверяем: подбор источников каталога по выбранным темам.
Предусловия: загружен `catalog_data.json` с пересекающимися тегами тем.
Шаги: 1) Вызвать подбор с единственной темой `metals_fx`. 2) Вызвать подбор
с парой тем (`tech_ai`, `macro`).
Ожидаемый результат: в набор входят только записи каталога, у которых
`topics` содержит выбранную тему; для пары тем — объединение; размер набора
не превышает лимита (~8) из плана §1.4.

ID: TC-02 | FR: FR-02 | Приоритет: P0 | Тип: unit
Что проверяем: ноль выбранных тем → дефолтный непустой набор.
Предусловия: каталог загружен.
Шаги: 1) Вызвать подбор с пустым списком тем.
Ожидаемый результат: возвращён дефолтный набор по приоритетным темам
(FR-02), набор не пуст.

ID: TC-03 | FR: NFR-03 | Приоритет: P0 | Тип: unit
Что проверяем: стабильность формулы `url_hash` (решение D19).
Предусловия: —.
Шаги: 1) Вычислить хэш для пар (url, title) дважды. 2) Вычислить для пар,
отличающихся только url; только title.
Ожидаемый результат: одинаковые пары → одинаковый хэш
(`sha256(url + '|' + title)`); любое отличие входа → другой хэш.

ID: TC-04 | FR: NFR-03 | Приоритет: P0 | Тип: unit
Что проверяем: идемпотентность сохранения элементов.
Предусловия: in-memory БД со схемой; один источник `rss`.
Шаги: 1) Сохранить 3 элемента из `rss_valid.xml`. 2) Повторно сохранить те
же 3 элемента. 3) Посчитать строки в `items`.
Ожидаемый результат: после второго прогона количество строк не изменилось
(дедуп по `UNIQUE(source_id, url_hash)`, `INSERT OR IGNORE`).

ID: TC-05 | FR: FR-13 | Приоритет: P0 | Тип: unit
Что проверяем: разбиение сводки при превышении 4000 символов (негативный
сценарий).
Предусловия: сборщик текста сводки (mock-LLM) и `rss_big.xml` (150+
элементов).
Шаги: 1) Построить текст сводки из всех элементов. 2) Разбить на сообщения.
3) Замерить длину каждого.
Ожидаемый результат: каждое сообщение ≤ 4000 символов; разрез только по
границам абзацев (ни один пункт не разрезан посередине); concatenация
сообщений восстанавливает исходный порядок пунктов без потерь.

ID: TC-06 | FR: FR-16 | Приоритет: P0 | Тип: unit
Что проверяем: экранирование опасных символов в заголовках, включая
«битый Markdown» (негативный сценарий).
Предусловия: заголовки из `rss_special_chars.xml`: `Q3 <b>drop</b> &
layoffs`, `strange _italic_ [x](y) *bold*` и т.п.
Шаги: 1) Собрать текст сводки с этими заголовками. 2) Прогнать через
строгий HTML-валидатор. 3) Сравнить отображаемый текст с исходными
заголовками.
Ожидаемый результат: все символы `< > &` экранированы; Markdown-символы
(`_`, `*`, `[x](y)`) выведены буквально, не превратились в разметку;
валидатор не нашёл ошибок; при отправке через `MockTelegramSender` нет
ошибок `can't parse entities`.

ID: TC-07 | FR: FR-11 | Приоритет: P0 | Тип: unit
Что проверяем: отбор элементов в окно дельты `[last_sent_at, now)`.
Предусловия: БД с элементами: старше окна, внутри окна, «будущие» (дата >
now), без даты публикации (fallback `fetched_at`).
Шаги: 1) Построить окно от заданного `last_sent_at`. 2) Отобрать элементы.
3) Повторить при `last_sent_at = NULL` (первая сводка).
Ожидаемый результат: попадают только элементы внутри окна; будущие и старые
исключены; элементы без даты оцениваются по `fetched_at`; при `NULL` окно
равно 24 часам (решение D9).

ID: TC-08 | FR: NFR-04 | Приоритет: P0 | Тип: unit
Что проверяем: ретраи HTTP-клиента с нарастающим backoff (негативный
сценарий).
Предусловия: http-клиент `bot/collectors/http.py` направлен на маршрут,
всегда отвечающий 500; таймеры заменены фейковыми.
Шаги: 1) Выполнить запрос. 2) Прочитать журнал вызовов мока времени.
Ожидаемый результат: ровно 3 попытки; паузы растут (1→2→4 с по плану §3);
завершение ошибкой источника, не зависанием; таймаут запроса задан
(connect 15 с / total 30 с).

ID: TC-09 | FR: FR-12 | Приоритет: P0 | Тип: unit
Что проверяем: вычисление следующего слота и условия catch-up.
Предусловия: FakeClock; функция расчёта слота из `bot/scheduler.py`.
Шаги: 1) Задать `send_times=["09:00","21:00"]`, `tz_offset_min=180`,
`last_sent_at` вчерашний. 2) Вычислить следующий слот. 3) Сместить часы на
сутки вперёд (симуляция сна), вычислить снова. 4) Повторить с иным
`tz_offset_min`.
Ожидаемый результат: слоты конвертируются в UTC по смещению; после
«просыпания» условие `now ≥ следующий слот после last_sent_at` истинно
(нужен catch-up); для будущего слота — ложь.
